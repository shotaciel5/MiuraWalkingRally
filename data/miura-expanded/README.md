OSM ID、元の座標/頂点列、歩行制約、建物、店舗/観光/歴史地物、標識等の必要タグを残す。編集者・連絡先・住所タグ等は取り込まない。要素とタグは安定ソートしLFで保存する。建物や目印の存在は全件の名称/入口/形状の完全性を意味しない。面の中心を入口としない。関係地物の取得情報だけで完全な面/標識位置や向きを推測しない。新しい周辺情報のコマ描画はまだ行っていない。

## オフラインの再現

Node 24.22.2を用い、リポジトリルートで実行する。サーバー・AWS・外部通信は不要。

~~~text
npm run roads:build
npm run roads:check
npm test
~~~

buildは固定osm.jsonのハッシュを照合し、roads.jsonとsource.json内の導出ハッシュ/件数を生成する。checkは既存導出物と比較し、変更しない。元データの歩行禁止/保留ルール、道路形状を変更しない。候補APIは軽量なroads.jsonのハッシュを確認して読む。データの検証失敗を無視して古い候補を表示しない。

## 意図的な再取得

通常の起動・ビルド・ブラウザ表示でOverpassへアクセスしない。更新が必要なときだけ、範囲/共有サーバーへの負荷を確認して明示実行する。既存ファイルがあるため、更新には --refresh が必要。

~~~text
npm run roads:fetch -- --refresh
npm run roads:build
npm run roads:check
npm test
~~~

初回でファイルがない場合は --refresh を省略できる。クエリは固定範囲1回、タイムアウト時に自動再試行・範囲拡大はしない。許可した取得先は既存と同じoverpass-api.deまたはoverpass.kumi.systems。再取得で全データのハッシュ/候補が変わるため、差分と生成への影響は再レビューする。[Overpass利用指針](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html)に従い、アプリの実行時バックエンドにはしない。

## 接続候補の評価と限界

初期178件すべてを覆い、線分への射影候補を自動計算できた。直線距離は中央値約7.5m、最大約141.2m、50m超は6件（50mは集計用で、採否基準ではない）。最大は灘ヶ崎で、地形・遊歩道・入口の確認が必要。これは幾何学的評価であり現地検証ではない。

施設代表点から最寄りの許容道路線分を探す。歩道のない車道も既存方針の対象で、明示的な歩行禁止・立入制限・未解決条件は除外/保留する。辺の向きを保持する。同距離はID順。追加/編集地点も現在の座標で再計算し道路IDを手入力しない。候補の丸と道路線分を表示し、施設からの点線は歩行経路として使わない。近傍道路と他地点がグラフ上でつながる保証もない。

ルート生成で候補点を採用する処理、候補の修正、全域の経路/コマ照合は後続。従来の「仮到達点3件・入口未確認83件・既存道路範囲外92件」は旧PoCの分類として維持し、新データでの生成可能判定と混同しない。
