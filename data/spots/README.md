## 候補と到達点

IDはosm-node/way/relationの種類と元IDを組み合わせ、名称やラリーのS/G/C1等の訪問役割から独立させています。分類はOSMタグに基づきます。営業現況・入場/撮影許可・公開時のチェックポイント利用可否は全件未確認で、reviewStatusはunverifiedです。

| routing.state | 件数 | 意味 |
| --- | --- | --- |
| poc-reference | 3 | 海南神社・光念寺・本瑞寺の既存PoCの仮ノードを参照。現地確認済みではありません。 |
| entrance-unverified | 83 | 施設代表点は既存道路データの矩形内ですが、入口や接続は未確認。 |
| outside-road-snapshot | 92 | 施設代表点は既存道路データの矩形外。道路拡張と接続確認が必要。 |

近傍道路への自動接続はしません。施設点が道路範囲内でも、歩行到達や安全性を保証しません。areaは緯度35.1376による「三崎周辺」「城ヶ島周辺」の便宜上の収集区分で、行政区域/島の境界判定ではありません。

同名の別支店・別神社は異なるIDのまま保持し、同名グループを確認用に出力します。近接したノード/ウェイや石塔等で同一性を判断できないものはreview.jsonで保留しています。名称の古い可能性がある「うらりカフェ」も保留し、確認前の名称変更や位置の補完は行っていません。

## ローカルで再現・検査する

対応するNode.jsを有効にしてプロジェクトルートから実行します。AWS・APIキー・サーバー起動は不要で、次のコマンドはネット接続しません。

~~~text
npm run spots:build
npm run spots:check
npm test
~~~

spots:buildは固定入力と採否記録からinitial-spots.jsonを生成します。spots:checkは出典/道路ハッシュ・仮到達点の参照・生成内容の一致を確認します。既存のdata/misakiと写真は書き換えません。JSONの改行は.gitattributesでLFへ固定しています。

## 明示的な再取得

データ更新が必要な場合だけ、[Overpass運用方針](https://dev.overpass-api.de/overpass-doc/en/preface/commons.html)と範囲・利用条件を確認して実行します。公開APIは実行時のバックエンドに使いません。

~~~text
node scripts/fetch-initial-spots.mjs --refresh
~~~

このコマンドはosm.json/source.jsonを更新するため、通常の再現確認では実行しません。更新後は採否記録・位置・重複・ハッシュを再レビューし、spots:build → spots:check → テストを実行してください。保留/到達点の元IDがなくなった場合は生成を止めます。P4-01cの運営者による追加/編集は、初期JSONとは別のSQLiteへ保存してIDで重ねます。spots:buildはSQLiteを更新せず、再適用で編集を取り消しません。編集済みの初期IDが新しい基礎データからなくなる場合は台帳の読込みを止めるため、無断で削除/ID変更せず移行を別途具体化してください。削除済みのIDは別の削除記録で保持し、再適用でも復活させません。完全消去・復元画面は今回作らず、既存の固定コース/参加記録を保持します。[削除方針](../../docs/decisions/010-spot-deletion.md)を参照してください。[保存方針](../../docs/decisions/009-local-spot-editing.md)を参照してください。
