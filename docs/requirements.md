# 写真連動型ウォーキングラリー Webアプリケーション 要件定義書

**バージョン：0.2（検討中）**

**ステータス：ドラフト・未確定事項あり**

2026-11-08追記：ユーザーの承認により、参加者側の追加開発を保留し、運営側のスポット管理・ルート/コマ地図生成を優先する。初期スポットの充実と運営者による追加・編集・削除を要望として反映した。各要件の必須/推奨は維持し、今回の実装順序は[バックログ](backlog.md)と[ADR-007](decisions/007-operator-first-development.md)を参照する。

## 1. プロジェクト概要

### 1.1 背景

三浦市では日帰り観光が中心となりやすく、観光客の市内周遊や滞在時間の延長、地域内消費の拡大が課題となっている。

本プロジェクトでは、観光客がコマ地図を頼りに地域を探索し、チェックポイントを巡るウォーキングラリー型Webアプリケーションを開発する。

また、運営者によるラリーの作成負担を軽減するため、ルートおよびコマ地図の自動生成機能を提供する。

### 1.2 目的

観光客が楽しみながら三浦市内のさまざまなスポットや店舗を巡る機会を創出し、地域内の周遊・滞在時間・観光消費の拡大を促進する。

### 1.3 サービスの基本方針

- **Webアプリ内で完結するウォーキングラリー**を提供する。
- 従来型のコマ地図を使い、観光客自身がルートを読み解きながら移動する。
- 指定スポットをチェックポイントとし、写真のAI判定またはQRコードによって訪問を認証する。
- チェックポイントの達成状況に応じてクーポンなどの特典を提供する。
- 店舗での購入は強制しない。
- 運営者は登録済みスポットを選択することを基本とし、ルートとコマ地図を可能な限り自動生成する。
- 運営者による手作業は、生成結果の確認・安全性の検証・必要最低限の修正に抑える。
- AIは必要な箇所に活用し、通常のアルゴリズムで実現できる処理に無理に導入しない。

## 2. 想定ユーザー

### 2.1 観光客

対象を特定の属性に限定せず、幅広い観光客を想定する。

例：

- 子ども連れの家族
- 友人同士やグループで訪れる人
- カップル
- ウォーキングや健康維持を目的とする人
- 観光しながら街を散策したい人

スマートフォンのWebブラウザから利用することを前提とする。

複数人で参加する場合、1台のスマートフォンを共有することを基本とする（仮）。

### 2.2 運営者

- 自治体・観光協会などの観光施策担当者
- 観光ラリーを企画・運営する関係者

運営者には、プログラミングや地図制作に関する専門知識を要求しないことを目指す。

## 3. サービスの利用フロー

### 3.1 観光客側

1. Webアプリにアクセスする。
2. 参加するウォーキングラリーを選択する。
3. ラリーの概要、所要時間、ルールなどを確認する。
4. ラリーを開始する。
5. Web上のコマ地図を頼りに歩く。
6. チェックポイントに到着する。
7. 写真のアップロード、またはQRコードの読み取りによって訪問を認証する。
8. 認証に成功するとチェックポイントが達成済みになる。
9. 次のコマ地図を確認し、ラリーを続ける。
10. 所定の達成条件を満たすとクーポンなどの特典を獲得する。
11. ゴールに到着してラリーを終了する。

### 3.2 運営者側

1. 管理画面で新しいラリーを作成する。
2. 登録済みのスポットからスタート・ゴール・チェックポイントを選択する。
3. 必要に応じて新しいスポットを追加する。
4. 所要時間などの基本条件を設定する。
5. ルートとコマ地図を自動生成する。
6. 生成結果を確認し、必要な場合だけ修正する。
7. チェックポイントごとの認証方法を設定する。
8. 特典と達成条件を設定する。
9. プレビューで確認してラリーを公開する。

### 4.2 スポットデータベース管理機能

ラリーに使用するスポットを、あらかじめデータベースに登録しておく。

運営者は登録済みスポットから選択するだけでラリーを構成できることを基本とする。

| ID    | 機能             | 概要                               | 優先度 |
| ----- | ---------------- | ---------------------------------- | ------ |
| SP-01 | スポット一覧     | 登録済みスポットを一覧表示する     | 必須   |
| SP-02 | スポット選択     | ラリーで利用するスポットを選択する | 必須   |
| SP-03 | スポット登録     | 新しいスポットを登録する           | 必須   |
| SP-04 | スポット編集     | 登録済みスポットの情報を修正する   | 必須   |
| SP-05 | スポット位置表示 | 地図上でスポットの位置を確認する   | 必須   |
| SP-06 | スポット検索     | 名称やカテゴリでスポットを検索する | 推奨   |
| SP-07 | スポット削除     | 運営者が不要なスポットを削除する   | 必須   |

#### 初期登録データと管理（2026-11-08追加）

初期状態から、地域のスポット候補をできるだけ多く登録しておく。運営者は初期スポットと自身で追加したスポットを編集・削除できるようにする。候補の収集を、生成機能の完成後まで一括して後回しにしない。初期件数・取得範囲・採用する情報源は、出典/利用条件・位置情報・重複・道路データの確認後に具体化する。

2026-11-08の追加指示により、神社・寺院に限らず、市場・鮮魚/産直、カフェ・飲食店、土産店、商店、公園・景観・小さな名所など幅広い候補を対象にする。

施設の位置と徒歩で到達する道路上の位置を区別する。候補登録だけで入口・通行・安全性を確認済みにはしない。P4-01dで、初期/追加スポットとも削除済みとして記録し、一覧・地図から外す方式を承認済み。固定デモで使用中のスポットも利用状況を示して台帳から削除でき、既存コース/参加記録を保持する。初期データ再適用でも削除状態を維持し、新しいコースの候補から外す。完全消去・復元画面は今回追加しない。初期ID/座標変更の移行や可変/公開ラリーとの整合はQ-15に残す。[ADR-010](decisions/010-spot-deletion.md)を参照。

#### スポットが保持する情報（仮）

- スポットID
- 名称
- 位置情報
- カテゴリ（店舗・景観・観光施設など）
- 説明文
- スポット写真
- チェックポイントとして使用可能か
- QRコード認証・写真認証の対応状況
- その他、ルート生成や認証に必要な情報

2026-11-08のP4-01cで、名称・カテゴリ・施設位置を必須、説明文を任意とする案を承認済み。施設位置は地図クリックまたは緯度経度で指定し、今回は現在の三崎・城ヶ島の候補範囲を対象とする。写真・QR設定・徒歩到達点の確認は後続で具体化する。[ADR-009](decisions/009-local-spot-editing.md)を参照。

### 4.3 ルート設計・生成機能

運営者が選択したスポットを通過する徒歩ルートを生成する。

ルートは必ずしも最短距離とせず、選択されたチェックポイントや経由地点を適切に巡ることを優先する。

| ID   | 機能                 | 概要                                 | 優先度 |
| ---- | -------------------- | ------------------------------------ | ------ |
| R-01 | スタート・ゴール設定 | 開始地点と終了地点を指定する         | 必須   |
| R-02 | チェックポイント設定 | 訪問させたいスポットを選択する       | 必須   |
| R-03 | ルート自動生成       | 設定条件から徒歩ルートを生成する     | 必須   |
| R-04 | 経由順序決定         | チェックポイントを巡る順番を決定する | 必須   |
| R-05 | ルート確認           | 生成結果を地図上で確認する           | 必須   |
| R-06 | ルート修正           | 運営者が生成結果を修正できる         | 必須   |
| R-07 | 距離・所要時間       | 推定距離・歩行時間を表示する         | 必須   |
| R-08 | 時間・距離条件       | 希望所要時間や距離を指定する         | 推奨   |
| R-09 | 寄り道ルート         | 最短経路以外のルートを生成する       | 検討   |
| R-10 | 複数候補生成         | 複数のルート案を提示する             | 検討   |

#### 基本方針

- 運営者が指定したチェックポイントを通過する。
- 可能な限り自動で経由順序・移動経路を決定する。
- 指定条件を満たす徒歩ルートを生成する。
- 最終的なルートの安全性は運営者が確認する。
- 不自然な往復や行き止まりなどをできるだけ回避する。

### 4.4 コマ地図生成・表示機能

従来型のコマ地図を基本とする。

交差点・分岐などを簡略化した図と進行方向を組み合わせ、観光客が地図を読み解きながら進めるようにする。

| ID   | 機能                 | 概要                                         | 優先度 |

| M-03 | コマ順序管理         | コマを進行順に表示する                       | 必須   |
| M-04 | Web表示              | スマートフォンでコマ地図を閲覧する           | 必須   |
| M-05 | チェックポイント表示 | 該当コマからチェックポイント詳細を確認できる | 必須   |
| M-06 | コマ地図編集         | 運営者が必要に応じて修正できる               | 推奨   |

| M-08 | ヒント表示           | 追加の道案内ヒントを提供する                 | 検討   |

#### 表示方針

- コマ地図はWebアプリ上で表示する。
- 紙への出力機能は実装しない。
- 従来型のコマ地図を基本とし、コマ内への風景写真やイラストの表示は原則不要とする。
- チェックポイントに到達するコマでは、スポット写真・名称・説明文などを別途表示する。
- コマ地図の自動生成結果は公開前に運営者が確認する。

### 4.5 チェックポイント認証機能

写真ミッションを独立した機能として扱わず、**スポットの訪問を認証するための手段**として位置付ける。

認証方法は以下の2方式を候補とする。

#### A. QRコード認証（簡易方式）

- 指定スポットのQRコードを読み取る。
- 正しいチェックポイントのQRコードであれば達成とする。

#### B. AI写真認証（発展方式）

- 指定スポットの風景・建物・看板などを撮影する。
- AIが写真に指定対象が含まれているかを判定する。
- 判定に成功した場合、達成とする。

| ID    | 機能         | 概要                                 | 優先度 |
| ----- | ------------ | ------------------------------------ | ------ |
| CP-01 | 認証方法設定 | チェックポイントの認証方法を設定する | 必須   |
| CP-02 | QRコード認証 | QRコードで訪問を記録する             | 必須   |
| CP-03 | AI写真認証   | 撮影写真をAIで判定する               | 検討   |
| CP-04 | 判定結果表示 | 達成・未達成を通知する               | 必須   |
| CP-05 | 再試行       | 判定失敗時に再度認証できる           | 必須   |
| CP-06 | 達成記録     | チェックポイントの達成状態を保存する | 必須   |

#### 未確定事項

- すべてのチェックポイントで同じ認証方式を使うか
- チェックポイントごとに認証方式を変更可能とするか
- AI認証用の基準画像をどのように用意するか
- 写真認証の判定精度をどこまで求めるか

生成結果に問題がある場合のみ、運営者が修正する。

## 5. AI・アルゴリズムの活用方針

AIやアルゴリズムは、ラリー制作の自動化およびチェックポイント認証に利用する。

| 対象         | 想定する処理                         | 方法                     |
| ------------ | ------------------------------------ | ------------------------ |
| ルート生成   | スポット間の徒歩経路と経由順序の決定 | 経路探索アルゴリズム     |
| コマ地図生成 | ルートから交差点図と進行方向を生成   | 道路データ解析・図形描画 |
| 写真認証     | 撮影した画像が指定スポットかを判定   | 画像認識AI               |
| ヒント生成   | 道案内の補足文などを生成             | 生成AI（検討）           |

### 基本方針

- AIの使用自体を目的としない。
- ルート・コマ地図は正確性と再現性を優先する。
- 運営者による大量の文章作成やミッション編集を必要としない。
- 生成AIによる複雑なミッション制作機能は、初期開発の対象外とする。

## 6. 非機能要件

### 6.1 利用環境

- スマートフォンのWebブラウザで動作する。
- 専用アプリのインストールを要求しない。
- 屋外で利用しやすい画面構成とする。

### 6.2 操作性

- 幅広い年齢層が直感的に利用できること。
- ラリーの進行状態が分かりやすいこと。
- 歩行中の画面操作をできるだけ減らすこと。
- 運営者が少ない操作でラリーを作成できること。

### 6.3 安全性

- 徒歩で通行可能なルートを使用する。
- 危険な道路や立ち入り禁止区域を避ける。
- 写真撮影による危険行動を誘発しない。
- 公開前に運営者がルートの安全性を確認できること。

### 6.4 プライバシー

- 写真・位置情報・参加履歴を必要最小限に取り扱う。
- 写真認証に不要な画像を長期間保存しない。
- 人物が写った写真の取り扱いに配慮する。

### 6.5 運用性

- 登録済みスポットを再利用できること。
- 新規スポットを運営者が追加できること。
- ラリーの公開後も内容を更新できること。
- 日常的な管理に専門的な技術知識を要求しないこと。

## 7. ハッカソンにおけるMVP

### 7.1 必須とする一連の体験

**運営者側**

1. 登録済みスポットを選択する。
2. チェックポイントを設定する。
3. ルートを自動生成する。
4. コマ地図を自動生成する。
5. 生成結果を確認して公開する。

**観光客側**

1. ラリーを選択する。
2. コマ地図を見ながら進む。
3. チェックポイントで認証する。
4. 進行状況を更新する。
5. ゴールし、クーポンを獲得する。

### 7.2 実装範囲を検討する機能

- AI写真認証
- ルートの複数候補生成
- 詳細なルート修正UI
- クーポン使用済み管理
- ヒント機能
- ラリーの複製

### 7.3 初期開発対象外

- ゲーム内アイテム
- 複雑なミッション生成
- ランキング
- 決済
- 宿泊予約
- 紙のコマ地図出力
- 高度な利用者別パーソナライズ
