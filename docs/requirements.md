## 1. プロジェクト概要

### 1.1 背景

三浦市では日帰り観光が中心となりやすく、観光客の市内周遊や滞在時間の延長、地域内消費の拡大が課題となっている。

本プロジェクトでは、観光客がコマ地図を頼りに地域を探索し、チェックポイントを巡るウォーキングラリー型Webアプリケーションを開発する。

また、運営者によるラリーの作成負担を軽減するため、ルートおよびコマ地図の自動生成機能を提供する。

### 1.2 目的

観光客が楽しみながら三浦市内のさまざまなスポットや店舗を巡る機会を創出し、地域内の周遊・滞在時間・観光消費の拡大を促進する。

### 1.3 サービスの基本方針

- ブラウザのコマ地図を頼りに、観光客が自分で道を読み解いて巡る。
- チェックポイントのコマで施設名と「写真を撮ろう」という案内を表示する。撮影は各自のスマートフォンのカメラを使う。
- 撮った写真はゴールでスタッフ等に見せる。アプリへの写真アップロード・撮影判定・訪問認証は行わない。
- QR認証・AI写真認証・クーポン/特典は対象外。競技としての不正防止・得点/順位や撮影枚数による進行制限を設けない。
- 事前にチェックポイント数を示してよいが、先の施設名は通常の参加者画面から表示しない。コマを手で先へ進めることは妨げない。
- 一覧から開始してコマへ進み、独立したコース詳細ページを必須にしない。コマ画面は地図と移動操作を中心にし、次のコマまでの距離・累積距離を表示しない。
- 店舗での購入は強制しない。運営者は登録スポット/経由地・訪問順を選び、ルートとコマを生成・確認して公開する。
- 道路解析・経路探索・図形描画はアルゴリズムを使う。生成AIやクラウドを利用すること自体を目的にしない。

## 2. 想定ユーザー

### 2.1 観光客

対象を特定の属性に限定せず、幅広い観光客を想定する。

例：

- 子ども連れの家族
- 友人同士やグループで訪れる人
- カップル
- ウォーキングや健康維持を目的とする人
- 観光しながら街を散策したい人

スマートフォンのWebブラウザから利用することを前提とする。

複数人で参加する場合、1台のスマートフォンを共有することを基本とする（仮）。

### 2.2 運営者

- 自治体・観光協会などの観光施策担当者
- 観光ラリーを企画・運営する関係者

運営者には、プログラミングや地図制作に関する専門知識を要求しないことを目指す。

## 3. サービスの利用フロー

### 3.1 観光客側

1. トップで楽しみ方を確認し、参加者の入口から公開コース一覧へ進み、コース名・概算距離/歩行時間・チェックポイント数などを見る。
2. コースを選んで開始し、コマ地図へ進む。通常の導線に独立した詳細ページは置かない。
3. コマ地図を読み解いて歩き、前後ボタンやスワイプで表示するコマを進める。
4. チェックポイントのコマで名称と撮影案内を見て、スマートフォンのカメラで写真を撮る。
5. ゴールに着いたら、撮影した写真をスタッフ等に見せる。アプリは写真の提出/合否や実際の到着を記録しない。

### 3.2 運営者側

1. 登録済みのスポットから開始・終了・チェックポイント/経由地を選ぶ。必要に応じて台帳へ追加/編集する。
2. 訪問順を設定して下書きを保存し、ルートとコマを自動生成する。
3. 地図/コマと入口・通行・安全性を確認し、必要なら道路上の到達点を修正して再生成する。
4. 確認した生成結果を保存し、参加者向けに明示公開する。
5. 必要に応じて公開停止/同じ内容の再公開を行う。内容を変える場合は再生成・別保存し、旧版を黙って差し替えない。

#### 初期登録データと管理（2026-11-08追加）

初期状態から、地域のスポット候補をできるだけ多く登録しておく。運営者は初期スポットと自身で追加したスポットを編集・削除できるようにする。候補の収集を、生成機能の完成後まで一括して後回しにしない。初期件数・取得範囲・採用する情報源は、出典/利用条件・位置情報・重複・道路データの確認後に具体化する。

2026-11-08の追加指示により、神社・寺院に限らず、市場・鮮魚/産直、カフェ・飲食店、土産店、商店、公園・景観・小さな名所など幅広い候補を対象にする。

施設の位置と徒歩で到達する道路上の位置を区別する。候補登録だけで入口・通行・安全性を確認済みにはしない。P4-01dで、初期/追加スポットとも削除済みとして記録し、一覧・地図から外す方式を承認済み。固定デモで使用中のスポットも利用状況を示して台帳から削除でき、既存コース/参加記録を保持する。初期データ再適用でも削除状態を維持し、新しいコースの候補から外す。完全消去・復元画面は今回追加しない。初期ID/座標変更の移行や可変/公開ラリーとの整合はQ-15に残す。[ADR-010](decisions/010-spot-deletion.md)を参照。

2026-11-09追記：道路範囲の拡張を可変生成より先行する。初期・追加・位置編集後のスポットは近くの歩行候補道路の線分へ自動対応付けし、道路IDの手入力を求めない。候補は施設代表点・実際の入口と区別し、通行確認済みにはしない。P4-03aのA案承認で、保存済み下書きから未確認の自動候補を使う生成プレビューを採用した。訪問順を維持し、到達不能/全区間0mは停止。候補修正・生成結果保存・公開は後続。[ADR-013](decisions/013-saved-draft-preview.md)を参照。[ADR-012](decisions/012-expanded-road-connections.md)を参照。

2026-11-09追記：P4-04のA案を承認。下書きごとの道路上到達点を選び直して保存し、施設位置・訪問順を保って再生成する。同じスポットの開始/終了は共通の補正とする。自動候補に戻せ、台帳・道路変更時は再確認する。修正後も現地未確認で、コマ手描き編集・生成結果保存/公開は後続。[ADR-014](decisions/014-draft-road-corrections.md)を参照。

### 4.3 ルート設計・生成機能

運営者が選択したスポットを通過する徒歩ルートを生成する。

ルートは必ずしも最短距離とせず、選択されたチェックポイントや経由地点を適切に巡ることを優先する。

| ID   | 機能                 | 概要                                 | 優先度 |
| ---- | -------------------- | ------------------------------------ | ------ |
| R-01 | スタート・ゴール設定 | 開始地点と終了地点を指定する         | 必須   |
| R-02 | チェックポイント設定 | 訪問させたいスポットを選択する       | 必須   |
| R-03 | ルート自動生成       | 設定条件から徒歩ルートを生成する     | 必須   |
| R-04 | 経由順序決定         | 運営者が下書きの並びで訪問順を指定する | 必須   |
| R-05 | ルート確認           | 生成結果を地図上で確認する           | 必須   |
| R-06 | ルート修正           | 運営者が生成結果を修正できる         | 必須   |
| R-07 | 距離・所要時間       | 推定距離・歩行時間を表示する         | 必須   |
| R-08 | 時間・距離条件       | 希望所要時間や距離を指定する         | 推奨   |
| R-09 | 寄り道ルート         | 最短経路以外のルートを生成する       | 検討   |
| R-10 | 複数候補生成         | 複数のルート案を提示する             | 検討   |

#### 基本方針

- 運営者が指定したチェックポイントを通過する。
- 訪問順は運営者が下書きで指定した並びを使う。開始・終了を固定し、途中地点を表示順に巡る。地点間の移動経路はアルゴリズムで求める。訪問順の総距離最適化は行わない（2026-11-09承認、ADR-012）。
- 指定条件を満たす徒歩ルートを生成する。
- 最終的なルートの安全性は運営者が確認する。
- 不自然な往復や行き止まりなどをできるだけ回避する。

従来型のコマ地図を基本とする。

交差点・分岐などを簡略化した図と進行方向を組み合わせ、観光客が地図を読み解きながら進めるようにする。

| ---- | -------------------- | -------------------------------------------- | ------ |
| M-01 | コマ地図自動生成     | 設定したルートからコマ地図を生成する         | 必須   |
| M-02 | 交差点・分岐表示     | 道路形状と進行方向を表現する                 | 必須   |
| M-03 | コマ順序管理         | コマを進行順に表示する                       | 必須   |
| M-04 | Web表示              | スマートフォンでコマ地図を閲覧する           | 必須   |
| M-05 | チェックポイント表示 | 該当コマで名称と撮影案内を表示。先の名称を事前に出さない | 必須 |
| M-06 | コマ地図編集         | 運営者が必要に応じて修正できる               | 推奨   |
| M-07 | 距離表示（運営者向け） | 計算/確認用に道路上距離を表示。参加者のコマ画面は区間/累積距離を出さない | 必須 |
| M-08 | ヒント表示           | 追加の道案内ヒントを提供する                 | 検討   |

#### 表示方針

- コマ地図はWebアプリ上で表示する。
- 紙への出力機能は実装しない。
- 従来型のコマ地図を基本とし、コマ内への風景写真やイラストの表示は原則不要とする。
- チェックポイントに対応するコマで名称と撮影案内を表示する。先の名称は通常の参加画面から出さず、紹介用写真の表示は必須にしない。
- コマ地図の自動生成結果は公開前に運営者が確認する。

2026-11-09追記：P4-04bのA案を承認。まず運営者プレビューの短い枝の保留を、元の角度・局所形状・全枝/進入基準と距離を保った自動拡大図＋30m参照図で確認する。建物/目印/標識・階段も同倍率で扱い、方向不明/欠落/不整合・読みにくい図は保留を継続する。通常コマ・参加者側・固定PoCは既定表示を保持。[ADR-015](decisions/015-operator-koma-expansion.md)を参照。

### 4.5 写真撮影の案内（訪問認証を廃止）

チェックポイントに対応するコマで「○○です。写真を撮ろう」と促す。参加者は各自のスマートフォンのカメラで撮影する。ブラウザのカメラ起動・撮影画像のアップロード/保存・AI判定は必要としない。

ゴールで撮影した写真をスタッフ等に見せる現地運用とする。写真を見せる相手・受付場所や時間などの具体的な運用は運営者が定める。アプリは撮影済み・訪問済み・受付済みを証明せず、画像の枚数・撮影順によるロックを設けない。

CP-01〜CP-06としていた認証方式設定・QR/AI写真認証・判定/再試行・達成記録は、2026-11-10の指示により対象外とする。コマを手で進めて先の名称を見ることへの不正防止は行わない。

### 4.6 クーポン・特典機能（廃止）

クーポン/特典の設定・発行・表示・利用管理・有効期限（C-01〜C-06、U-08/U-12、A-08）は要件から撤回する。後続で実装する保留機能とは扱わない。新たに必要となった場合だけ別の要件として検討する。

| A-03 | ルート・コマ地図生成 | 選択条件から自動生成する       | 必須   |
| A-04 | 結果プレビュー       | ルート・コマ地図を確認する     | 必須   |
| A-05 | ラリー公開           | 確認済みのラリーを公開する     | 必須   |
| A-06 | ラリー編集           | 作成済みラリーを修正する       | 必須   |
| A-07 | スポット管理         | スポットデータを登録・編集する | 必須   |
| A-08 | 特典管理（廃止） | 要件から撤回 | 対象外 |
| A-09 | ラリー複製           | 既存のラリーを元に新規作成する | 検討   |

#### 運営者UIの基本方針

運営者は、基本的に選択・確認操作によってラリーを作成できることを目指す。

ルートやコマ地図を一から手作業で作成することは前提としない。

2026-11-08のP4-02では作業中の下書きを1件保持し、地点を選んで保存した後にコース生成へ進む使い方を採用する。下書き名・開始/終了を保存時の必須、途中のチェックポイント/経由地を任意とし、開始と終了は同じ地点を使える。確認待ちの地点も下書きとして保存できるが、生成/公開可能を保証しない。台帳変更・削除は保存済み下書きに表示して再確認する。2026-11-09のB案承認で、途中地点の並びを訪問順として使用する方針へ更新した。地点間の経路は自動生成し、訪問順を最適化しない。[ADR-012](decisions/012-expanded-road-connections.md)を参照。[ADR-011](decisions/011-working-rally-draft.md)を参照。

生成結果に問題がある場合のみ、運営者が修正する。

## 5. AI・アルゴリズムの活用方針

| 対象 | 処理 | 方法 |
| --- | --- | --- |
| ルート生成 | 運営者指定の訪問順でスポット間の徒歩経路を決める | 経路探索アルゴリズム |
| コマ地図生成 | 道路の接続と座標から分岐・進行方向を描く | 道路データ解析・図形描画 |
| 写真撮影 | 現地で参加者へ撮影を促す | 表示のみ。画像認識AI・アップロード/判定は使わない |

同じ入力/固定データからの再現性を重視する。生成AIの採用を目的にしない。ヒントなど別の追加機能は、必要性を確認し人間が選ぶまで実装しない。

## 6. 非機能要件

### 6.1 利用環境

- スマートフォンのWebブラウザで動作する。
- 専用アプリのインストールを要求しない。
- 屋外で利用しやすい画面構成とする。

### 6.2 操作性

- 幅広い年齢層が直感的に利用できること。
- ラリーの進行状態が分かりやすいこと。
- 歩行中の画面操作をできるだけ減らすこと。
- 運営者が少ない操作でラリーを作成できること。

### 6.3 安全性

- 徒歩で通行可能なルートを使用する。
- 危険な道路や立ち入り禁止区域を避ける。
- 写真撮影による危険行動を誘発しない。
- 公開前に運営者がルートの安全性を確認できること。

### 6.4 プライバシー

- 撮影写真・画像メタデータ・GPS位置や、ゴールで見せた写真をアプリへ収集/保存しない。
- 匿名の開始ID・コース版・開始日時を同じタブ内に保存し、公開状態確認で参加記録をサーバーに送らない。
- 現地の撮影では人物や施設の利用条件に配慮する。撮影画像は参加者自身の端末で扱う。

### 6.5 運用性

- 登録済みスポットを再利用できること。
- 新規スポットを運営者が追加できること。
- ラリーの公開後も内容を更新できること。
- 日常的な管理に専門的な技術知識を要求しないこと。

## 7. ハッカソンにおけるMVP

### 7.1 必須とする一連の体験

**運営者側**

登録スポット/経由地と訪問順を選択 → ルート/コマを生成 → 確認/必要な補正 → 保存/公開。

**観光客側**

公開コースを選んで開始 → コマ地図を読み解いて進む → チェックポイントのコマで名称と撮影案内 → 各自のカメラで写真を撮る → ゴールで写真を見せる。

最後のコマを表示しても、実際の到着/撮影/受付を自動認定しない。従来の固定デモの達成ボタン/終了記録は検証履歴であり、新しい参加者フローの必須機能ではない。

### 7.2 実装範囲を検討する機能

- 閲覧コマ位置の復元
- 運営導線や試用コースの整備
- 詳細なルート修正UI
- ラリーの複製
- 必要性を確認したヒント

### 7.3 初期開発対象外

- QR認証、AI写真認証、画像アップロード/判定
- クーポン/特典の設定・発行・利用管理
- 得点・競技順位、不正防止、GPSによる到着判定
- ゲーム内アイテム、複雑なミッション生成
- 決済、宿泊予約、紙の地図出力、高度な個人別最適化

## 10. 視覚的な目印の検証依頼（2026-11-11）

ユーザーはコマ図から建物形状/建物等の名称を省き、現物を見分けられる少数の交通記号等と、店舗の固有看板/モニュメントの写真・アイコンを検討する方針を示した。今回はキー不要の表示PoCとMapillary/画像認識の調査を実施し、通常画面への採用は比較レビュー後に決める。トークンがない状態で実API取得/物体認識を実施済みとは扱わない。

コマ生成/参加者操作のたびのAPI呼出し・画像処理を避け、重要交差点等を絞った事前取得・採用素材の保存/再利用を検討する。画像カバレッジ、対象物位置と進入方向からの見え方、利用条件・保存量/期限/失効・認識方式は未決定。[検証範囲と未決定事項](visual-landmarks-poc.md)。QR/AI認証・クーポン廃止の要件は維持する。

## 11. ルート上の目印取得と運営者の採用方針（2026-11-12）

ユーザーは「ルートを作ってから該当交差点だけ準備し、再利用する」方針を承認した。全候補を運営者が採用/不採用にでき、一時停止・横断歩道に対応する候補を初期採用、信号・固有物等を初期不採用とする。候補の確かさを区別し、停止点から標識の現物、横断箇所から塗装形状を補作しない。得られた候補の初期採用であり、実物の網羅的な検出を保証しない。

今回は設定済みトークンを使うPoCとして実取得/画像切り出し/採否/専用保存を一連で検証するよう承認済み。既存公開コースを変更せず、参加者への適用と画像/出典の保存版統合は後続。[仕様と制限](route-landmark-poc.md)、[ADR-021](decisions/021-route-landmark-review-poc.md)。

## 12. 階段と写真候補の再現性（2026-11-12）

ユーザーはPoCで階段も必須にし、Mapillaryによる特徴的な対象の切り抜き写真を候補へ表示し、新しいルートでも取得できる再現性を求めた。階段は記録のある道路属性として常時表示し、写真等の採否では消さない。写真は位置/検出領域・出典を持つ候補から準備し、初期不採用を保つ。

下書きから生成したルートに対応する取得・切り出し・再利用をGUI/CLIで同じ手順にし、固定例の手動投入に依存しないことを実データで検証する。記録/画像がない場合や品質不足を区別し、任意の新ルートで必ず写真が得られるとは保証しない。[仕様と検証](landmark-preparation-poc.md)。

## 13. 初期デモデータの同梱（2026-11-12）

ユーザーは、AWSへの移行を妨げない構成で少数の初期データを同梱する方針を承認した。固定コース2件と画像/地物・出典を配布し、トークンがない別環境でも同じデモを試せるようにする。画像の版/切り抜き/作者と地物の利用条件を保持する。実DB/運営状態/秘密情報はGitへ入れず、明示したローカル登録で既存データを上書きしない。AWS保存先の選定/移行・通常公開版の写真統合を今回確定しない。[仕様](bundled-demo-data.md)。

## 14. 地域の事前取得と公開アプリのMapillary取得禁止（2026-11-12）

ユーザーは開発PCで地域全体を取得し、地物ID/座標/出典と128×128の切り抜きを配布し、公開アプリが索引から採否を選ぶ方針を承認した。ルート生成時や画面からMapillaryを呼ばず、トークンの誤設定でもWeb取得を拒否する。画像のない地点・範囲外を区別する。OSM背景タイルは変更しない。[仕様](region-landmarks.md)。

2026-11-12追加：切り抜き写真がない固有物（店舗看板・広告・旗/バナー等）は、運営者のコマ候補・図・採用数から除外する。交通記号と必須の階段は継続する。候補の表示と保存APIで同じ条件を使う。
