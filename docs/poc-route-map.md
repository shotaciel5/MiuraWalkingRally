## 3. 対象地点列：三崎下町の短い周回区間（P2-01承認済み）

### 3.1 候補と選定理由

**三崎港 → 海南神社 → 光念寺 → 本瑞寺 → 三崎港**をPoCの対象地点列とする（P2-01承認済み）。S1のコースCから、三崎港を出発して同じ港へ戻る三崎下町の徒歩区間だけを切り出す。城ヶ島へのバス移動と城ヶ島内の散策は対象に含めない。

選定理由は、公式散策資料に連続する訪問順と区間値があり、短い範囲で複数地点と港への復帰を照合できること。高台へのアクセスも含むため、道路情報が徒歩経路・入口・高低差を扱えるかという限界も確認する。選定理由は開発上の評価であり、安全性やバリアフリーの確認結果ではない。

  C1 --> W1["経由地候補：光念寺"]

## 4. 参照ルートと観察箇所の作り方

### 4.1 参照ルートと自動生成結果を分ける

1. S1の2ページ目で対象区間の案内経路を確認し、開始位置・各施設の入口・復帰位置を候補として記録する。現段階は地点列と経路範囲の案であり、道路ノード列や座標列は未確定。
2. P2-02で利用できる道路・経路情報を確認した後、交差点の接続と歩行可能なアクセスを照合し、手作業の参照ルートを具体化する。矛盾する資料は出典と更新時点を記録し、正解を推測しない。
3. 比較対象の参照ルート・入口・観察点を固定してから、同じ入力条件で自動生成する。生成結果を見て都合よく参照ルートを書き換えない。
4. 自動生成では指定地点の通過を確認する。参照経路と異なっても、別の徒歩経路として成立する可能性は分けて扱い、道路接続・通行条件・対象地点・比較条件をレビューしてから評価する。

最初のコマ生成評価では訪問順を固定する案とする。これは基本設計H-02に基づくPoC条件であり、R-04の経由順序自動決定を不要とする仕様変更ではない。自動の順序決定を評価していない場合は、そのまま未検証と記録する。

## 5. 評価条件・合否基準（P2-01承認済み、未決定事項は継続）

### 5.1 共通条件

- 徒歩のルートを扱い、S → C1 → W1 → C2 → Gの順をPoCの比較条件案とする。同じ開始・終了地点だからといって空の経路や距離0へ短絡させない。
- コマは重要な分岐・交差点と、チェックポイントへ到達する箇所を中心にする案とする。案内が必要な分岐の一覧を、生成前の参照ルート確認で作る。
- コマの向きは、進入方向を基準に進む枝が読み取れる表現を候補とする。図の上方向・単純化規則、角度の許容差は未決定。
- 距離は、コマに対応する位置から次の位置までの徒歩経路に沿う累積距離を候補とする。直線距離と混ぜず、測定位置・単位・丸め方法を明示する。採用する定義はレビューで確認する。
- 「合格」「不合格」「判定保留」「対象外」を分ける。情報がなく確認できない項目を合格に含めない。

### 5.2 確認項目

| ID | 対象 | 確認方法 | 合否の基準 |
| --- | --- | --- | --- |
| E-01 | 地点・訪問順 | 生成経路の開始・終了、各入口と通過順を参照ルートに照合する。 | 合意した地点を順に通り、各地点まで歩行経路が接続する。地点の欠落・順序違い・建物代表点への誤接続は不合格。入口や接続未確定なら保留。 |
| E-02 | 徒歩通行・安全 | 道路情報の属性、公式規制情報、必要な現地確認を照合する。 | 通行禁止・危険な誘導が確認された経路は不合格。歩行可否・横断・規制が未確認なら保留。道路データ上の適合だけで公開安全性の合格にしない。 |
| E-03 | 分岐の接続・枝 | 観察点ごとに進入・退出・他の枝を、生成コマと根拠資料で並べて見る。 | 確認できた道路の接続を保ち、進む枝を識別できる。誤った接続、重要な枝の欠落、存在しない枝の描画は不合格。形状の根拠不足は未確認として示し、完全な図の生成は保留。 |
| E-04 | 進行方向・コマ順序 | 参照ルートを順にたどり、コマを使って選ぶ枝と次のコマの位置を照合する。 | 左右・進入/退出・順序が一致する。逆向き、選ぶ枝の取り違え、必要なコマの欠落は不合格。方位・表現規則が未合意なら表示仕様の判定は保留。 |
| E-05 | 距離・推定時間 | 合意した測定位置と計算方法で区間値を照合し、累積値・単位・丸めを確認する。S1の値は概算比較にだけ使う。 | 値と根拠を追跡でき、区間・累積の対応が一致する。直線距離との混同・区間の取り違えは不合格。絶対誤差・相対誤差を記録し、精度の許容値が未合意なら精度の合格を出さない。時間は採用した歩行速度等の算出条件を併記する。 |
| E-06 | 情報不足・生成失敗 | 欠落データや接続不能を含むケースを、外部サービス選定後の検証で用意する。 | 問題箇所と理由を確認できる。推測の交差点を確定図として出す、失敗を成功扱いにする場合は不合格。 |
| E-07 | ブラウザでの読解 | 実装後、スマートフォン幅で図・方向・順序・チェックポイント・距離を実道路の参照と照合する。 | 停止して読むことで対象の分岐を識別でき、表示の対応を追える。表示された事実だけを合格理由にしない。対象端末・読解評価の方法は実装前に確認する。 |

評価結果には、実行日、入力データの版、参照資料、期待結果、実際の結果、合否、未確認の理由を記録する。角度・座標・距離精度の数値閾値は未決定とし、精度判定を行う前に根拠を示して承認を得る。

PoCの技術評価と、観光客へ公開できる安全性の評価は別に残す。保留があっても技術的な限界の調査は記録できるが、全体を「実用性・安全性確認済み」と報告しない。

## 8. P2-01で合意した点と継続課題

1. 対象は三崎港から海南神社・光念寺・本瑞寺を経て戻る短い徒歩区間とし、CP候補2か所・経由地1か所で検証すること。開始・終了・入口の正確な位置は道路情報と安全確認の結果で決める。

### 9.5 承認済みの採用構成

**案A：OSMを公開Overpassから限定取得して固定保存し、TypeScriptで小さな徒歩グラフ探索とコマ生成を検証する構成**をローカルPoCに採用する（ユーザー承認済み）。探索はまず固定訪問順の区間ごとに距離を評価する最小方式（Dijkstra法を候補）とし、経由順序の最適化を完成済みにはしない。具体的な歩行ルール・計算方法はP2-04の着手時に設計する。

推奨理由は、アカウント・キー・AWSなしで対象地域の道路構造を取得できたこと、同じ取得時点の道路を経路とコマの根拠に使えること、小範囲の検証に外部エンジンの運用を増やさずに始められること。徒歩ルールを実装する負担とデータ不足は受け入れる必要があり、成立しない場合は限界を記録して案Bなどを再検討する。推奨は本プロジェクトの判断であり、経路の実用性を実証した結果ではない。

承認された範囲は、案Aを初期PoCのデータ・処理構成として採用し、OSMの出典・ODbL表示を伴う小範囲データで評価すること、公開Overpassは限定的な取得にだけ使うこと。本番の地図・経路サービスやAWSバックエンドは確定しない。

案Aの承認を受け、選定記録をADR-001に残した。続くP2-03ではAWS公式の互換性を再確認してWeb実行環境を選定・実装した。構成と検証結果は10節、保守上の注意はADR-002に記録する。

### 12.1 抽出ルールと測定の定義

[抽出処理](../lib/route/junctions.ts)を追加し、[固定データ用の接続](../lib/misaki-junctions.ts)を通して生成経路・手動参照の両方へ適用した。新たな地図ライブラリ・クラウド依存・データ取得は追加していない。

[OSMのデータモデル](https://wiki.openstreetmap.org/wiki/Elements)を基に、元のwayの隣接nodeを接続根拠とする。wayは道路線と面の境界の両方を表し得るため、area=yesの外周や工事・計画中の線は枝として使わない。[layerの説明](https://wiki.openstreetmap.org/wiki/Key:layer)も参照し、同じ座標・線の交差だけで別IDの点を接続せず、立体交差から架空の分岐を作らない。ただし、共有IDが現地で正しい接続になっていることの独立検証は別に必要。

| 対象 | 今回の実装・仮の測定条件 |
| --- | --- |
| 候補にする位置 | 開始・終了・指定の到着点、隣接する異なるnodeが3個以上の位置、入った枝へ戻る位置。曲がっているだけの2枝の形状点を角度閾値で候補化していない。 |
| 枝数 | way数ではなく隣接node数。同じ隣接点へ複数のwayが接続する場合は1枝にまとめ、元のway IDと各通行判定を保持する。1本でも候補があれば枝は候補、候補なしで保留があれば保留、全て除外なら除外とする。 |
| 探索と枝の違い | 徒歩禁止の道路も接続根拠があれば他の枝として残す。各枝の隣接1区間について、徒歩の進入・退出を候補/除外/保留に分ける。道路全体の通行可否ではない。 |
| 再訪・区間境界 | 全4区間を順序付きの点列へ連結。区間境界の到着点は1通過として扱い、後で同じnodeへ戻れば別通過として保持。node IDだけで候補を重複排除しない。 |
| 北基準の角度 | 北0°・時計回り、0以上360未満。分岐から隣接nodeへの初期方位角を球面上で計算する。枝の角度は外向き。 |
| 進入・退出の向き | 進入の向きは、分岐から進入元へ向く枝の方位角を180°反転したもの。退出は分岐から退出先へ向く方位角。進入元での初期方位と分岐での進入の向きを混同しない。 |
| 相対角 | 進入方向を0°とし、正が時計回り/右、負が反時計回り/左。範囲は[-180°,180°)、同じ枝への折返しは−180°。直進/右折等へ分類する角度閾値は未採用。 |
| 距離 | 今回の仮の定義として、この通過位置から次の候補・到着点まで元の道路形状に沿って累積する。省略した形状点も含む。内部は丸めず、画面はmを四捨五入、角度は小数1桁。最終候補の次距離はnull（終了）とする。 |
| 不足・曖昧さ | 同一点座標などで方向を定められなければnull、条件不明の障害物・範囲外の接続はreviewとし、確認事項を画面に表示する。欠落参照・不整合な経路・距離はエラーで停止する。 |

内部の同じデータ同士の整合検査には1e-6mの数値計算上の許容値を使う。これはGPS・道路形状・距離精度の合否閾値ではない。角度の精度は直近線分の長さやOSM形状の粒度に依存し、丸め表示も実際の交差角の精度を保証しない。

### 12.5 自己レビューと停止点

- 順序・方向・距離：同一nodeの再訪と区間境界の到着を区別し、枝を数える基準を隣接IDにした。進入方向は分岐位置での向きとして扱い、他の枝や折返しを消さない。次候補までの距離は直線ではなく、形状点を含む元の辺列の部分和と照合した。
- 情報不足：不明な角度を作らず、制限のある枝を描画根拠から黙って消さない。現地の接続・道路形状の欠落、OSMの誤接続、複雑な交差点や極端に短い線分の妥当性は机上だけでは確定できない。今回確認事項フラグが0でも、現地安全性の確認済みを意味しない。
- 範囲・過剰設計：小さなTypeScript処理と固定データ接続を追加し、新しい依存・DB・管理画面・AWS SDKを導入していない。P2-06のコマ描画・単純化・公開案内は実装していない。
- 未決定：Q-01/Q-02の最終のコマ向き、候補の省略・統合、角度・距離精度の合否閾値は未承認のまま。今回の測定条件を最終表示仕様へ無断で昇格しない。P2-04からの実入口・到着/認証位置・経路差の採否・現地規制/安全性・訪問順の自動決定も継続課題。

P2-05をコミットしてレビューを求め、ここで停止する。次の候補はP2-06「従来型コマ地図のブラウザ表示」。着手前に表示の向き・省略と距離表示の条件を確認する。P2-06、Phase 3、AWS操作は実施しない。
