# P4-06f-1：コースの公開・非公開切替の仕様案

- 日付：2026-11-10
- 状態：次の小タスクとして仕様を整理。下記A案の採用は未決定。アプリ/API/DBは変更していない。
- 基準：[要件A-05/A-06、6.5節](requirements.md)、[保存版の固定ADR-016](decisions/016-saved-course-snapshots.md)、[公開/開始ADR-018](decisions/018-published-participant-courses.md)、[バックログ](backlog.md#publication-lifecycle)。

## 1. コースの意味と今回の目的

コースは、運営者が開始・終了・チェックポイント・経由地と訪問順を選び、生成して保存したもの。公開した道順は固定する。以前の文書の「可変コース」は固定デモと区別する呼び方だったため、今後は「作成したコース」「公開したコース」と書く。参加中に道順が変わる機能や、別のコース種別は追加しない。

現在は保存済み詳細から公開できるが、公開後に非公開へ戻せない。次はこれを解消する一つのストーリーに絞る。内容を変えるときはスポット/経由地を選び直して再生成する既存の流れを使い、参加中の保存版を上書きしない。

## 2. 提案する最小範囲

運営者の保存済み詳細で「公開を停止する」を選び、対象名と参加者への影響を確認して実行する。保存済みコースは残し、参加者一覧から外す。取り消しや保存失敗では状態を変えたと表示しない。

停止した同じ保存版は、改めて対象と影響を確認して再公開できる。公開/非公開は参加者への掲載状態であり、コース削除や台帳のスポット削除とは分ける。過去の保存済みを自動公開しない。未公開/公開中/公開停止を運営者に区別して表示する。

| 含める | 後続・含めない |
| --- | --- |
| 公開停止と同じ保存版の明示的な再公開 | 保存済みの編集/削除・下書きへの復元 |
| 状態/日時と対象名・影響の確認、再送/競合/失敗への対応 | 公開内容を別の保存版へ一括差替する専用機能 |
| 公開中だけの参加者一覧、停止URLと開始済み記録の扱い | 参加履歴の自動移行、長期/端末間保存 |
| 既存SQLiteを使うローカル運用 | QR/特典、達成/ゴール、認証/認可・AWS配信 |

## 3. 採用確認が必要な参加者の扱い

**A案（推奨）：公開停止後は、新規開始を止め、開始済みでも次にサーバーから画面を読み込む時点でコマを開けなくする。** 開始記録は消さず、停止中の案内とコース一覧へのリンクを表示する。同じ保存版を再公開すれば、同じタブに残る参加ID/開始日時を引き継ぐ。

| 観点 | A：次回読込から閲覧停止 | B：開始済みの参加者は継続 |
| --- | --- | --- |
| 参加者一覧 | 停止コースを除外 | 同じ |
| 停止した詳細/コマURL | 停止中を案内し、コマ/開始操作を提供しない | 開始済みだけ元の版を提供する必要がある |
| 開始前の古い画面 | 開始/再開の操作前に公開状態を再確認する | 開始済み/新規を区別して確認する必要がある |
| 保存済みの開始記録 | 保持し、同じ版の再公開時に再利用する | 保持して継続する |
| 実装への影響 | サーバーの公開状態を一律に適用できる | 現在はタブ内記録だけなので、サーバーが継続対象を判定する仕組みが別途必要 |

B案を選ぶ場合、sessionStorageの自己申告を権限の証明と扱わず、継続可能な参加記録をどう扱うかを追加で設計する。今回は必要な公開切替を小さく進めるためAを推奨する。

Aも、すでにブラウザへ読み込まれた図や保存された画像を遠隔で回収する機能ではない。開いているコマ画面は再読込まで残り得る。全コマ操作での常時照会・自動停止/通知は初回へ含めず、「即座に全端末を停止する」とは表示しない。停止前に発行された画面/事前読込の再利用を考慮し、開始/再開操作と新しい画面取得では最新の状態を確認する。

未公開/不明IDは従来どおり見つからない扱いとする。停止中はコース名や図を配信せず一般的な停止案内とし、破損/読取失敗を停止中や0件に偽装しない。開始記録も勝手に削除/初期化しない。

## 4. 保存・再送と競合の最小方針案

承認後、現在のSQLite v6をv7へ移し、公開状態とその変更版・直近の操作日時を保持する。既存の公開行は公開中として移し、公開日時・コースID/指紋を保持する。未掲載コースは未掲載のまま。保存済み形式v1と開始記録形式v3は変えない。

コース内容の版と公開状態の変更版を分ける。同じ保存ID/指紋の停止・再公開ではコース内容を変えず、参加IDを作り直さない。状態変更では対象/指紋と画面が読んだ状態の版を照合し、短いトランザクションで更新する。変更版や内部項目は運営操作の裏側で扱い、参加者へ設定させない。

- 同じ操作の二重送信や成功応答消失後の再送では、成立済みの同じ結果/日時を使う。
- 他の画面で状態が変わっていたら確認を求め、古い画面から黙って上書きしない。
- 「公開→停止→再公開」の後に、最初の停止要求が遅れて届いても再停止しない。
- 停止後に古い公開要求が届いても、勝手に再公開しない。公開情報を単に削除して未掲載へ戻す方式は使わない。
- 記録の破損/未対応形式や移行失敗を初期化せず、失敗時はロールバックする。

UI/API/repositoryの境界と同一Origin/JSON・小さい要求/no-storeを継続する。新しいサービス・依存や認証は採用しない。具体的な型/APIの項目は承認後に実装に必要な分だけ決める。

## 5. コース内容を変えたい場合

スポット/経由地/順序を選び直して下書きを保存→再生成→確認→別の保存済みコースとして保存する。運営者が新しいコースの公開と旧コースの停止をそれぞれ明示実行する。片方の操作で他方が自動実行されるとは扱わず、同時差替の保証も追加しない。既存の固定版を黙って差し替えたり、参加者の記録を別コースへ移したりしない。

この流れは既存のADR-016/018を維持する整理で、下書き復元・更新履歴・公開版の系譜を作る新しい基盤ではない。差替専用の操作が必要になれば後続で選ぶ。

## 6. 承認後の受入条件

- 公開→停止→再公開を明示操作で切り替え、再起動後も状態/日時と保存内容を保持する。取り消し・保存拒否は状態を変更しない。
- 参加者一覧は公開中だけを表示する。未公開/不明/停止/破損を区別し、他コースと固定デモに影響しない。
- Aの場合、古い詳細からの開始と停止URLの再読込でコマへ進めず、停止案内を表示する。既存記録を保持し、同じ版の再公開後に元の参加ID/開始日時を使う。
- 再送/応答消失/同時操作・公開→停止→再公開後の遅い要求を検証し、状態を巻き戻さない。
- v6→v7で台帳編集/削除・下書き/補正・保存済み/公開情報を保持し、欠落/異物/破損を初期化しない。
- コース生成・コマ/距離/目印を変えず、公開/停止/開始の失敗、3画面幅・操作/出典、既存の生成/保存・固定デモを回帰確認する。
- 実DBを試験データで変更せず、ローカルの専用DBで検証する。AWSや一般参加受付は実行しない。

## 7. 今回のレビューと終了点

現在の公開repository・公開確認UI・参加者の開始保存/サーバー側読取を読み、停止機能が未実装であることと、開始記録がタブ内だけにあることを確認した。A/Bの違いと、読み込み済み画面・遅延要求の限界を仕様へ記載した。まだ実装や移行を成立済みとは扱わない。

今回は用語/仕様とバックログを更新し、文書の差分・相対リンク/表・保護対象を自己レビューしてコミットする。アプリ/型・単体/ビルド・HTTP/ブラウザは文書だけのため再実行しない。採用前にADRを確定せず、A/Bを人間へ提示して停止する。
