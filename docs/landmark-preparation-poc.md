# 階段の必須表示とルート別の写真候補準備（P2-10）

2026-11-12。ユーザー依頼：PoCの階段を必須にし、Mapillaryの特徴的な対象の切り抜きも候補へ載せ、新しいルートでも取得できる再現性を確立する。[ADR-022](decisions/022-reproducible-landmark-preparation.md)に採用方針を記録する。

## 使い方

1. スポット/訪問順を選んで下書きを保存し、通常の生成プレビューでルートを作る。
2. 「このルートの目印を選ぶ（PoC）」から /operator/landmarks/review?source=draft へ進む。
3. トークンが設定されていれば、未取得地点と少数の写真候補を自動準備する。1回は最大20地点。残りがあれば「目印と写真候補を準備」で続ける。
4. 「切り抜き写真の候補」に画像・作者/撮影日・原画像/ライセンス・対応コマが表示される。「コマ○で確認」で該当コマへ移動し、一覧/図の採否を選び、保存する。
5. 階段は道路上の必須情報として表示する。目印の採否や初期状態への戻しで消えず、右側に出典道路と必須表示の説明を出す。

写真は初期不採用。一時停止/横断候補の初期採用と全候補の選択は前タスクを継続する。階段は選択型POIとは別の道路属性なので採否チェックを設けない。OSMに記録された階段区間だけを使い、ハッチングは実際の段数を示さない。短い正の区間も無条件に省かず、元の全枝/座標/進行方向は維持する。図が保留のものを階段/写真で解決済みとは扱わない。

通常の保存済みコース/公開版・参加者画面への採用反映は今回も行わない。階段の必須表示はこの専用PoCに適用し、既存の通常図の表示条件は変更しない。

## 同じ方法をコマンドでも実行する

Node/npmの版と通常の起動手順は[README](../README.md)を参照。.env.localのサーバー専用MAPILLARY_ACCESS_TOKENを使用し、値をコマンド引数へ書かない。Client secret・AWSは不要。

保存済み下書きから、最大200地点の範囲でそのルートだけを準備する：

```powershell
npm.cmd run landmarks:prepare -- --source draft --max-junctions 200
```

**同じコマンドを再実行し、JSONのrequestCounts.graph / imagesが両方0であることを確認する。** 入力・固定データ・キャッシュ・処理版を変えていなければdatasetId、写真候補の順序/出典と切り抜き範囲を再利用できる。再実行で失敗した候補へ無制限にAPIを呼ばない。

外部通信せず、準備状況だけを確認する：

```powershell
npm.cmd run landmarks:prepare -- --source draft --cache-only
```

固定例を調べる場合だけ --source sample を指定する。実処理にはスポットID/画像ID・手動投入したサンプルを埋め込んでいない。新しい下書き/順序からルートを再計算し、その地点と候補を取得する。GUIとCLIは同じ準備エンジンと対象選択を使い、各操作でサーバーのルート指紋を照合する。

| JSON項目 | 意味 |
| --- | --- |
| datasetId | 生成したルート/コマ/OSM候補の指紋 |
| targets / preparedTargets / remainingTargets | このルートに必要な地点と取得済み/残り |
| photoCandidates | 同じ条件で同じ順に調べる地物ID。写真の有用性を保証するIDではない |
| readyPhotos / qualityMisses | 保存画像のある写真候補数/品質条件に合う画像を得られなかった候補数 |
| requestCounts.graph / images | この実行での外部API/画像取得回数。ローカル画面/APIの通信回数ではない |
| photos | 地物ID・元画像ID・処理版・切り抜き範囲（roi）・対応コマ番号。再実行の対応確認に使用 |
| stairsCards | 階段の記録があるコマ数 |
| errors | 認可/通信/保存等の未完了。秘密情報や外部応答本文は出さない |

CLIは取得に失敗した場合1、地点数の上限で残りがある場合2、完了/キャッシュ参照は0を返す。写真がない/品質不足は理由を伴う結果で、架空の画像や位置を生成しない。

## 準備ルールと再利用

- 道路のコマを先に生成する。対象は生成コマの付近だけで、地域全域の画像を先取りしない。現在の三崎・城ヶ島の固定道路データで生成できるルートが対象。
- 地点情報は1回20地点ずつ。旧仕様の「先頭20地点以降を拒否」を廃止し、未取得地点から再開する。CLIは明示した上限1〜200地点を処理できる。
- コマから30m内に入る地物のうち、位置と検出領域のある店舗看板/広告/バナーを写真候補にする。対象の推定位置を使い、カメラ位置を対象物位置とみなさない。
- ルート内の地理的な偏りを抑える固定順序を作り、地物IDを重複させず最大8候補を調べる。店舗看板を先にし、画像のある3候補を目標にする。すでに手動等で準備済みがあれば3件より多く表示できる（一覧の最大12件以外も該当コマの候補で確認）。
- 同じ地点・写真は再利用する。画像の品質条件と処理版2は前タスクを継続し、切り抜きはブラウザCanvasで作る。任意のモニュメント検出/店名OCR・パノラマ歪み補正は実装していない。
- 品質条件に合う画像なし、という結果も24時間保存する。期限内の自動準備では同じ失敗を再取得せず、手動の「写真を再確認（再取得）」なら再試行できる。通信/認可エラーを品質不足として保存しない。
- 準備中も図を操作でき、停止後は完了済みの結果を残す。認可/制限エラーや複数回の通信失敗で処理を止める。別ルートの応答で現在の編集状態を置換しない。
- ルート切替は入力の指紋をキーにして画面を更新し、以前のルートの候補を新しいルートとして表示しない。

PoC用の保存上限は地点200、写真20、採用状態50ルート、画像なしの結果100件。地点/画像の再利用は7日、品質不足の再利用は1日。期限で物理削除する意味ではなく、既存結果の自動消去はしない。キャッシュ更新やMapillary側の更新後も永続的に同じ写真になるという保証ではない。保存先は既存のLANDMARK_POC_DIRで分離可能。

トークンは.env.localからサーバーで読む。API認証はヘッダのみ、画像CDNへは送らず、ブラウザ/JSONレポート/画像のメタデータ/ログ/Gitへ値を含めない。画像・実取得データ・QA下書きはGit対象外。取得元・作者・ライセンスと利用条件は[前タスクの確認](route-landmark-poc.md#利用条件の確認2026-11-12)を継続し、一般配信条件の再確認は残る。

| 既存ブラウザ回帰 | 両モードで公開6コース全227コマ、短枝の拡大/参照図、公開停止/再公開、参加記録、名称非表示、トップの操作を確認 |
| 実取得 / 再現 | 上表の3ルートを同じCLIで実行。再実行の外部取得0回、入力指紋・元画像ID・処理版・切り抜き範囲・対応コマを確認 |

ブラウザQAは実取得済み画像/メタデータを専用保存先へ複製して実施。三崎では以前から準備済みの画像も含む4候補を表示し、自動準備の目標3件を超える既存画像も残ることを確認した。自動取得だけの初回実測は上表の3件。画像URLに元画像ID/処理版を含め、保存された切り抜き範囲と異なる画像を返さないことも確認した。

自己レビューでは、専用PoCだけに必須階段を適用し、通常表示の既定動作・道路形状・保留条件を維持した。新規依存/DB形式変更はなく、GUIとCLIに取得ロジックを二重実装していない。元のローカルDB・固定OSM/スポットデータ・提供写真11ファイルのハッシュを作業前と比較し、変更がないことを確認。秘密情報・取得画像・キャッシュ・QAファイルをコミット対象から除外した。

現地/スマホ実機・対象物位置や進入方向からの可視性・通常保存/公開版への採用反映・一般配信条件の再確認・AWSは未実施。古い撮影日や対象物の撤去もあり得るため、取得成功だけで参加者用の目印として確定しない。
