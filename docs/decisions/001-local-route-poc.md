# ADR-001：OSM固定データとTypeScriptによるローカルPoC

- 日付：2026-11-06
- 状態：承認済み（ユーザーの「案A承認します。次に進んでください」に基づく）
- 対象：Phase 2のローカルPoC。商用公開・AWSバックエンドの選定は含めない。
- 関連：[比較・取得記録](../poc-route-map.md)、[基本設計](../design.md)

## 決定

OSMを公開Overpassから限定取得し、出典・取得時点・クエリ・ライセンスとともに小範囲の固定データとして保存する。経路探索とコマ生成は、同じ取得時点の道路を根拠としてTypeScriptで検証する。

最初は固定の訪問順で区間ごとの探索を行う。Dijkstra法を候補とし、具体的な計算・歩行ルールの実装はP2-04で設計する。経由順序の自動決定は未検証として残す。

公開Overpassは必要なデータを限定取得する用途に使い、観光客の常時バックエンドにはしない。OSMの帰属表示とODbLに対応する。アカウント・キー・AWSをローカル起動の前提にしない。

## 歩行ルールに対するユーザーの追加指示

歩道の存在は必須条件にしない。自動車が通れる一般道路は、歩道なし・歩道タグなしを理由に一律除外せず、徒歩経路の候補に含める。既存の徒歩専用路も対象であり、自動車が通れないことを理由に除外しない。

この方針は候補としての扱いであり、一般道路の現地安全性を確認済みとするものではない。明示的な歩行禁止、自動車専用区間、立入制限、工事等は別に判定する。特定の地域には自動車専用道路がない、という仮定をコードへ埋め込まない。

次の例をP2-04で経路フィルターを実装する際の受入条件へ引き継ぐ。

| 入力・状況 | 期待する扱い |
| --- | --- |
| 一般道路、歩道なし、徒歩禁止の情報なし | 歩道なしだけでは除外しない。徒歩の経路候補とし、必要な安全確認を残す。 |
| 一般道路、歩道・footタグの情報なし | タグ不足だけを理由に一律不可にしない。既定の歩行ルールと確認事項を明示する。 |
| 歩行禁止・自動車専用・立入制限が明示される | 車が通れても、その情報を無視して候補化しない。 |
| 徒歩専用路・参道等 | 車が通れない理由だけで除外しない。通行条件を確認する。 |
| 条件付き制限・barrier・タグが矛盾する | 優先順位や例外を実装前に決め、未解決なら確認対象として残す。 |

三浦縦貫道路のような自動車専用区間が周辺にあり、[県警は高速道路・自動車専用道路への歩行者等の立入り不可を案内](https://www.police.pref.kanagawa.jp/kotsu/jiko_boshi/kosoku/mes87001.html)している。一方、[県のⅡ期案内には片側歩道を持つ断面の記載](https://www.pref.kanagawa.jp/docs/wk7/miurajukan/index2.html)もあるため、同じ路線名全体を一律に扱わず、区間の条件を確認する。

今回は承認と方針の記録まで。歩行フィルター、実道路との照合、現地確認はまだ実施していない。

## 理由と影響

対象地域でnode・way・接続参照を取得できた。小さな固定データから始めることで、経路とコマの根拠を追跡しながら外部サービス運用を増やさずに検証できる。一方、徒歩ルールの実装、データ欠落・入口・境界の確認は自分たちで担う必要がある。

比較したORSとGoogle Routesは初期PoCに採用しない。固定データで成立しない場合は、限界を記録して再検討する。今回のデータ取得は道路の通行許可や安全性の証明にはならない。
