# ADR-011：作業中のラリー下書きを1件保持する

- 日付：2026-11-08
- 状態：承認済み。1件案を提示後、ユーザーは「下書きが一度に複数いらない」、完成後はコース生成へ進む使い方と回答した。
- 対象：P4-02。地点の選択・下書きの保存まで。
- 関連：[設計23節](../design.md#p4-02-design)、[バックログ](../backlog.md#operator-first)、[運営画面7節](../operator-app.md#p4-02)、[削除方針](010-spot-deletion.md)

## 決定

作業中の下書きは1件とし、複数下書きの一覧・切替を今回作らない。地点を選んで保存した後、次のP4-03aでその内容からコース生成へ進む。保存は既存のローカルSQLiteと同じファイル・保持範囲を使う。公開や参加者向けコースの追加は別タスクとする。

下書き名（1〜100文字）、開始1件・終了1件を保存時に必須とし、途中のチェックポイント/経由地は任意とする。途中地点は同じIDを1件とし、役割を変更できる。開始と終了は同じスポットを使え、途中地点との共用も許す。開始/終了と途中の訪問は別の役割として記録する。

途中地点の追加順と上下移動は入力を整理するための仮の並びであり、生成の訪問順を確定しない。要件の「可能な限り自動で経由順序を決定」を維持し、R-04のアルゴリズム・制約はP4-03aで確認する。現在の入力に対する距離・所要時間・道順を生成済みとして表示しない。

## 地点と保存の扱い

有効な台帳から地図/一覧・名前/ジャンル/エリアで選ぶ。入口未確認・道路データ範囲外も確認待ちとして下書きに含められる。仮到達点のある3件も現地確認済みではない。下書き保存を生成可能・歩行可能の保証にしない。

同じSQLiteのrally_draftにworkingという固定キー1件を持ち、明示操作で保存/更新する。各役割のスポットID・保存時の台帳情報/版、下書きの版・保存日時を保持する。再読込み/サーバー再起動で復元する。閲覧だけでは下書き行を作らない。未保存の入力は画面内のみで、ページ移動前に保存が必要である。

既存DB形式v1/v2からv3へ移行し、スポット追加/編集・削除記録を維持して下書きテーブルを追加する。移行と版更新はトランザクションで行う。保存前にアプリを停止してファイルをバックアップする。旧コードとのロールバックは対応するバックアップと組にする。

## 台帳との整合と再確認

下書きは保存時の地点情報を保持する。台帳の変更や削除で、保存済みの下書きを黙って書き換えない。

- 読込み時に現在の台帳と照合し、変更/削除された役割と地点を示す。運営者が最新情報を反映して確認し、削除済み地点は外すか選び直して再保存する。
- 保存時は同じDBトランザクション内で有効なID/台帳の版を照合し、削除済み/不存在・古い台帳情報による保存を拒否する。クライアントから座標等を任意の保存情報として受け入れない。
- 台帳の初期データが更新され、運営者の版が0のままでも、読込み時に保存済みの名称/位置等との差を検出する。初期ID再編などの移行規則は引き続きQ-15に残す。
- 別の画面で下書きが更新された場合は古い別内容の上書きを拒否する。入力を控え、保存済みの読直しを明示操作で行う。
- 応答が失われた場合も、現在の保存内容と同じ再送では保存済みの版/日時を変更しない。保存失敗・不明時は入力を残し、確定した応答を確認するまで成功表示しない。
- 下書きの破損/不明な保存形式はエラーとし、空の下書きで置換しない。

台帳の最新情報の反映は下書きの自動保存ではない。下書きの保存・編集は既存の固定デモコース/版と参加進捗へ反映しない。P4-01dの固定コースを保つ削除方針を継続し、可変の下書きでは上記の再確認を行う。公開済みの可変ラリーとの整合はP4-06等で具体化する。

## 技術上の範囲

DB接続/移行を共通のローカル処理へ分け、スポット照合と下書き保存を同じトランザクションで行えるようにする。入力/読込みの純粋な処理はUIから分ける。既存のLeaflet地図を再利用し、ルートの線や架空の到達点を補わない。

APIは既存と同じローカル同一オリジン・JSON・no-storeを使い、下書き入力の本文上限は64KiBとする。ログイン/権限・AWSバックエンドの選定を追加しない。SQLiteをAmplify Hostingの永続保存先にはせず、移行時に保存処理とAPI条件を交換する方針はADR-009を継続する。
