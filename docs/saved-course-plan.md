# P4-06a：生成結果の保存・再表示の最小仕様案

- 日付：2026-11-09
- 状態：P4-06a時点の仕様案と検証履歴。ユーザーがA案「下書き1件＋保存済みコース複数」を明示承認。採用後の仕様は9節・ADR-016、実装/検証は運営画面16節を参照。
- 前提：作業中の下書きは1件（[ADR-011](decisions/011-working-rally-draft.md)）。現在は下書き/到達点補正だけをSQLite v4へ保存し、生成結果は画面内（[ADR-013](decisions/013-saved-draft-preview.md)、[ADR-014](decisions/014-draft-road-corrections.md)）。
- 次の価値：生成したルート・コマ・目印を、再読込みや再起動後にも、保存した内容で確認できるようにする。
- 関連：[バックログ](backlog.md#saved-course-plan)、[設計31節](design.md#saved-course-design)、[運営画面15節](operator-app.md#p4-06a)。

## 1. 推奨するA案と代案

**A案：下書きは1件のまま、保存済みコースは複数残し、一覧から開く。保存済みを上書きしない。**

例えば三崎周回を保存した後、作業中の下書きを城ヶ島コースへ変更して生成・保存する。保存済みの一覧から、どちらも当時の内容を閲覧できる。下書きを複数作る操作や切替は追加しない。保存後も下書き/補正を自動で空にせず、そのまま編集・生成を続ける。

| 比較 | A：複数の保存済みコース（推奨案） | B：最新の生成結果1件だけ |
| --- | --- | --- |
| 保存する内容 | 計算済みのルート/コマ/目印と元の入力条件 | 同左 |
| 異なる結果を保存 | 新しいコースとして追加。以前の保存を保持 | 保存済みの1件を、対象と版を確認して明示上書き |
| 後から見る内容 | 選んだ保存時点の内容 | 最後に保存した内容。上書き前の結果は残らない |
| 下書き | 現状と同じ1件 | 現状と同じ1件 |
| 台帳/道路更新 | 保存済みへ自動反映しない | 同左 |
| 主な画面 | 保存→保存済み詳細、保存済み一覧→詳細 | 保存→最新1件の詳細 |
| 適する使い方 | 作ったコースを残して別のコースも作る | ハッカソン等で最新1件だけあればよい場合 |

Aで残る複数件は、作業中の下書きや編集できる版履歴ではなく、確定した計算結果の保存コピー。同じ名称でも生成条件/結果が異なれば別の保存となり、一覧の保存日時・距離・コマ数で区別する。厳密な「ラリーID＋版」の更新履歴は、公開/参加中データと接続する際に別途設計する。

以下はA案を実装する場合の最小仕様。Bを選んだ場合は上書き/競合・古い詳細リンクの扱いをB用に修正してから実装する。どちらもまだ採用していない。

## 2. 操作と画面

~~~mermaid
flowchart LR
  D["作業中の下書き：1件"] --> G["生成プレビュー"]
  G --> S["この結果を保存"]
  S --> V["保存済みコース詳細：非公開"]
  L["保存済みコース一覧"] --> V
  D --> E["下書きを編集・再生成"]
  E --> G
~~~

提案する操作は以下。

1. /operator/previewの生成済み結果に「この結果を保存」を追加。保存成功時に、その保存済み詳細を開く。生成するだけでは保存しない。
2. 運営者タブへ「保存済みコース」を追加。一覧には名称・保存日時・道路上距離・コマ数・確認事項を表示し、詳細へ進む。
3. 詳細は保存時の訪問順・全体地図・全コマ/出典・目印・30m参照形状と拡大表示を閲覧できる。保存日時、当時の道路データ時点、「保存済み・非公開・現地未確認」を示す。
4. 詳細で行うのは閲覧/図の表示切替だけ。台帳・下書き・補正を変更する操作と、「現在の下書きから再生成する」操作を保存済みコースの編集として見せない。
5. 戻る導線は保存済み一覧と、別の作業であることが分かる「作業中の下書きへ」。保存済みから下書きへの復元/複製、上書き編集・削除/復元・公開は今回追加しない。

名称/スポット等の別入力フォームは追加せず、保存元の下書き名・条件を使う。画面URL案は/operator/coursesと/operator/courses/[id]。これらは未実装の提案URL。

## 3. 保存するものと「同じ内容」の意味

| データ | 保存する内容 |
| --- | --- |
| 保存記録 | 保存ID、保存日時、保存形式の版、生成処理の識別版、生成内容の指紋 |
| 入力条件 | 下書き名/版/日時、選択したスポットの当時の情報と役割/訪問順、到達点補正と版 |
| 元データ | 道路/補足情報のハッシュ、OSM時点・帰属等の出典 |
| 計算結果 | 道路上距離/概算時間・区間/経路、全体図の道路点列、全コマ/分岐/役割/距離/出典、周辺情報、短い枝の30m参照形状と参照用周辺情報、保留理由/注意 |

現在の[生成処理](../lib/operator/rally-preview.ts)が返す配列/数値/文字列中心のモデルを基礎に、保存形式v1として明示的に定義・検証する。TypeScriptの推論型をそのまま将来までの保存契約としない。Graph/Map・React要素、元OSM全体、タイル、画面の画像、参加者情報は保存しない。

閲覧時は保存された計算結果を使い、現在の台帳/下書きやOSMから再生成しない。後から施設名・座標・削除状態・道路データが変わっても、当時の内容を保ち、台帳へスポットを復活させない。OSMの外部リンクは現在の原典への参照で、当時の状態を保証するものではない。

「同じ内容」は訪問地点・経路/距離・コマ/元形状・目印/出典等の保存値が同じであること。画面幅、選択中のコマ、地図の拡大、参照図の開閉、レイヤー切替は保存しない。レスポンシブな拡大や文字/色の描画は対応するビューで行い、将来までスクリーンショットの完全一致を保証するものではない。未対応の保存形式を、最新の再計算で黙って置換しない。

## 4. 保存時の一致確認・再送・競合

画面で確認した結果と違うものを保存しないため、表示時に、入力条件・生成処理の版・出典と生成結果から安定した指紋を計算する。キーを正規化し、配列の順序を保ったJSONを基礎にする。指紋は同一性確認と重複保存の識別用で、認証の代わりにはしない。

保存のPOSTでは指紋と下書き/補正の版・出典識別等だけを送り、ルート/コマ全体は受け取らない。

- 同じ指紋の保存が既にあれば、保存データの形式/整合と要求との対応を確認し、既存のID/保存日時を返す。応答だけ失われた後の再試行や連打で同じ保存を増やさない。既存の同じ保存の取得は、保存後に下書き/台帳が変わっていても当時の記録を返せる。
- 未保存なら、現在の下書き・台帳・補正を同じ読取トランザクションから取得。版/内容・出典が表示時と一致するか確認し、サーバーで生成した結果の指紋も照合する。
- 計算中に下書き/台帳/補正が変わり得るため、書込トランザクションで生成元を再照合する。違っていれば競合として止め、表示済み結果を残して最新内容からの再生成を案内する。
- 同じ結果を別画面で同時保存した場合も、指紋の一意制約と再読取で1件にする。計算中はSQLiteの書込ロックを持ち続けず、重い処理と確定書込を分ける。
- 下書きなし、台帳/補正の不整合、到達不能、全区間0m、データ読込/計算失敗では保存しない。
- 生成が成立していて図に保留/注意が残る場合は、その情報も含めて確認用に保存できる案とする。保存は安全確認/公開可否の承認ではない。
- 保存失敗・応答不明を成功扱いせず、表示を残して同じ内容で再試行できるようにする。ID/保存日時を確定してから保存済み画面へ進む。

## 5. 保存先・実装の最小境界

A案が承認された場合は、既存のSPOT_DB_PATHのSQLiteへsaved_courses相当の表を追加する案。例として保存ID・一意な生成指紋・保存値JSONを持つ。グローバルDB形式v4→v5の移行で、スポット編集/削除・下書き・補正を保持する。未対応形式・欠落/破損・移行失敗を勝手に初期化しない。保存モデル自身の形式v1と、SQLite全体のv5、参加者進捗のv3は別の版。

UIは保存先を直接扱わず、既存のoperator API/repository境界を継続する。追加APIは保存用POST /api/operator/coursesを最小候補とし、一覧/詳細ページはNodeサーバーで保存データを読む。使わないAPIやクラウド向けアダプタ群を先に作らない。現在の同一ローカルOrigin・JSON・no-store等を継続する。

一覧には概要だけを渡し、詳細で保存形式・指紋・値の整合を検証して表示する。不正/破損や未対応の記録を表示できると報告せず、エラーと再試行を案内して保存値を保持する。古い保存を読むときに、現在の台帳照合/生成処理を呼ばない。保存済みを削除したスポットの存在確認へ依存させない。

既存のプレビューの図/操作を再利用する場合も、保存済みの閲覧と作業中の下書きの操作を明確に分ける。保存のために新しい認証・Cognito・QR/クーポン・参加者コースを追加しない。AWS/Amplify Hosting移行時の永続保存先は別途比較・承認し、ローカルSQLiteをそのまま本番永続DBとしない。

容量/時間の上限、保存IDの具体形式、細かなエラー文と一覧の詳細な実装は、承認後のタスクで必要な深さに決める。上限を超える場合はデータを省略して成功扱いにせず、明示的に止める。

## 6. メモリー上の成立性確認

2026-11-09、固定OSMと初期台帳の代表5例で、入力条件＋現在の計算結果をJSON化し、復元値の深い一致と正規化後の指紋一致を確認した。実DBへアクセスせず、アプリ・元データを変更せず、外部通信なしで実行した。これは保存機能や保存形式v1の実装/検証ではなく、シリアライズの小さな確認。

## 7. 承認後の最初の小タスクと完了条件

P4-06bとして「生成→明示保存→保存済み一覧/詳細」を一つのユーザー価値にまとめ、必要なUI/API/ローカル保存を同じタスクで実装する案。公開/参加者側は含めない。

| 確認する場面 | 完了条件 |
| --- | --- |
| 保存・再起動 | 保存IDを開き直して訪問順/距離/全コマ/目印/参照図が一致。画面幅に応じた拡大も使える。 |
| 連打・応答消失・同時保存 | 同じ指紋は同じID/保存日時、別内容を誤って上書きせず、失敗時に表示を保持する。 |
| 保存前/計算中の変更 | 下書き/補正/台帳・出典や生成条件の変化を拒否し、別の結果を黙って保存しない。 |
| 保存後の変更/削除 | 台帳/下書き/補正や道路が変わっても保存済みの計算値は保持。閲覧で再生成や台帳の復活を行わない。 |
| 保留・エラー | 保留図/注意を保持。到達不能/0mは保存不可。破損/未対応形式/書込失敗を初期化せず明示する。 |
| 移行と回帰 | v4→v5で旧データ保持、失敗をロールバック。通常図・参加者固定コース/記録、既存補正操作を保持。 |
| 画面 | 保存済みからの操作で別の作業中下書きを編集したと誤解させない。1280/390/320px・再読込/再試行を確認。 |

今回の文書だけで、保存数・上書き方式・保存形態や公開可否を確定しない。採用承認後にADRを作成し、上の小タスクだけを実装して再度停止する。

## 9. A案承認後の採用内容

ユーザーがA案を明示承認し、P4-06bを実装。[ADR-016](decisions/016-saved-course-snapshots.md)と[運営画面16節](operator-app.md#p4-06b)が現在の仕様・検証記録。第1〜8節はP4-06a当時の比較/試算/終了点の履歴として保持する。

下書き1件＋保存済み複数を採用。保存済みは上書きせず、同じ結果の再送は元のID/日時を返す。入力と計算結果・出典・保留を形式v1へ固定し、現在の台帳/道路や再生成へ依存せず一覧/詳細から閲覧する。既存SQLiteはv5へ移行し、旧データを保持する。

保存IDはUUIDv4、生成器識別子はoperator-preview-v1、最大8MiB/件。クライアントは小さな指紋/版/出典だけを送り、サーバー再計算と保存直前の入力照合で表示結果との一致を確認する。公開・参加者側・保存済みの編集/削除/復元・AWSは今回含めない。
