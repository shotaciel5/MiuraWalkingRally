# 三浦市ウォーキングラリー — 開発の背景・目的とソリューション

作成日：2026-11-14
対象：現在のローカル実装。要件定義v0.3と、その後の承認済み変更を反映する。

> 食事や有名スポットへの訪問に、まちを読み解く小さな冒険を加える。
> 参加者が「もう一か所歩きたい」と思える体験を、運営者がつくり続けられるようにする。

## 1. なぜ、このアプリを開発したのか

### 背景：三浦に来た人に、もう少し長く、広く楽しんでもらう

コンテスト実施要項では、周遊・滞在を促し、観光消費を拡大する「三浦ディープステイ」が上位の目的として示されている。提供されたテーマヒアリングまとめでも、滞在時間と観光客一人当たりの消費額を増やすことが重視されている。

ヒアリング資料には、昼食を目的に訪れてそのまま帰宅したり、別の観光地へ移動したりする短時間滞在と、十分に知られていない地域資源への誘客が課題として挙げられている。また、繁閑差を踏まえ、既存の店舗や観光資源を活かす視点が示されている。

そこで私たちは、**すでに三浦を訪れた人が、食事の前後にまちを巡る理由をつくること**に着目した。市場、カフェ、土産店、路地、海の景色、小さな名所などを、一続きの徒歩体験として楽しめるようにする。

現在の対象は三崎・城ヶ島周辺である。この範囲で周遊体験を成立させ、三浦市内の滞在と消費機会を増やす入口をつくる。宿泊への接続は上位目的との関係として捉え、現段階で宿泊予約や泊食分離の仕組みを提供しているとは扱わない。

### 課題：訪れるきっかけと、体験をつくる仕組みの両方が必要

| 視点 | 解決したい課題 | この企画での捉え方 |
| --- | --- | --- |
| 観光客 | 食事や有名スポットの周辺に、ほかに何があるのか気付きにくい | 情報提供に加え、実際に歩いて出会う動機をつくる |
| 観光客 | 追加でどこへ行くか、どう歩くかを組み立てる必要がある | 選んですぐ始められる、まとまった徒歩体験を用意する |
| 地域 | まだ知られていない場所や店舗への立寄りにつながりにくい | 運営者が訪れてほしい場所をコースへ組み込めるようにする |
| 運営者 | 道順や交差点のコマを一つずつ制作すると、準備・更新の負担が大きくなる | 企画と確認に集中できるよう、経路探索と図の作成を自動化する |

地域課題は提供資料に基づく。参加者の行先選びの負担や運営者の制作負担は、それらを解くために置いた本プロジェクトの課題仮説であり、利用者調査による定量的な検証はこれから行う。

## 2. 目的と対象者

**コマ地図を読み解く楽しさで徒歩周遊を促し、三浦市内の滞在時間と立寄り先を増やす。その体験を、運営者が少ない制作負担で用意できるようにする。**

この目的を、参加者向けの体験と運営者向けの作成支援の二つで実現する。

| 対象 | 想定する人・利用場面 | 提供する価値 |
| --- | --- | --- |
| 主な参加者 | 食事や観光で三崎・城ヶ島を訪れ、前後の時間に散策できる日帰り観光客 | 追加の行先を探し回らず、遊びとしてまちを巡れる |
| 一緒に楽しむ参加者 | 家族、友人同士、カップルなど、相談しながら歩きたい人 | 道や目印を見比べ、発見や写真を共有できる |
| 主な運営者 | 自治体・観光協会、観光ラリーを企画する担当者 | 登録スポットと訪問順から作成し、確認・公開できる |
| 地域の受益者 | 飲食店、カフェ、土産店、観光施設など | 知ってもらい、立寄りや利用につながる機会が増える |

店舗や団体との導入・提携が成立しているという意味ではない。現在の画面は日本語で、外国語対応や、あらゆる身体条件に合うルートの保証は今後の検討・確認を要する。

## 3. 解決のアイデア：道を読むこと自体を、観光体験にする

### 参加者には「コマ地図で巡る小さな冒険」

コマ地図は、分岐の形・入ってきた方向・進む方向を、一場面ずつ示す地図である。目の前の道とコマを見比べる行為が遊びになり、道中の路地や看板、景色にも目を向けるきっかけをつくる。

1. ブラウザでコースを選び、ログインなしで開始する。
2. コマを前後に切り替えながら、自分たちのペースで歩く。
3. チェックポイントのコマで地点名と撮影案内を見る。写真は各自のスマホカメラで撮る。
4. ゴールでは写真をスタッフ等に見せ、発見を振り返る体験を想定する。

事前にはチェックポイント数などの概要を示し、名称は該当コマで表示して発見する楽しみを残す。先のコマも手で閲覧できる。コマ画面は地図を中心にし、次のコマまでの距離は表示しない。

写真提示は現地の運用であり、アプリは到着・撮影・写真の合否を判定しない。ゴールの受付方法は今後決める。

### 運営者には「訪れてほしい場所から、コースをつくる道具」

1. 地図や一覧から、開始・終了・チェックポイント・経由地を選び、訪問順を決める。
2. 下書きを保存して、ルートとコマを生成する。
3. 道順・コマ・目印を確認する。必要なら道路上の到達点や目印の採否を修正する。
4. 現地の入口・通行・安全性を確認したうえで、コースを保存・公開する。

例えば、市場から始めて、路地の名所、カフェ、海沿いの景色を巡る、といったテーマを人が企画する。訪問順を保ちながら、その間の道順や図の作成をシステムが支援する。

現在は重複を整理した初期スポット89件を用意し、市場・飲食・カフェ・土産・景観・名所などから選べる。運営者による追加・編集・削除もでき、登録件数はその後の編集で変わる。

~~~mermaid
flowchart TB
    A["運営者がテーマ・地点・訪問順を決める"] --> B["経路とコマを自動生成"]
    B --> C["運営者が道順・目印・安全性を確認して公開"]
    C --> D["参加者がコマを読み解いてまちを巡る"]
    D --> E["発見・写真・店舗への立寄りのきっかけ"]
    E --> F["滞在時間と観光消費機会の拡大を目指す"]
~~~

最後の二段は期待する行動変化と効果であり、実測済みの成果ではない。

## 4. 実現する技術とAIの役割

| 処理 | 現在の方法 | 利用者にとっての意味 |
| --- | --- | --- |
| スポットを道へつなぐ | 施設位置から近くの歩行候補道路へ自動対応付け。道路上の到達点は地図で修正できる | 道路IDなどの専門的な設定を減らす |
| 地点間の経路を求める | 運営者が決めた訪問順を保ち、道路距離を重みに最短経路を探索する | 人が企画した立寄り先を順に巡れる |
| コマを作る | 道路の分岐・形状・進行方向を解析して描画する | 元の道路に基づく図を、同じ条件で再現できる |
| 道なりのコマを省略する | ルールで重要地点を保護し、学習済みモデルが紛らわしい場面を追加で残す | コマの多さを抑えつつ、読み間違えやすい場面の案内を支援する |
| 目印を選ぶ | OSMの地物と、事前準備したMapillary由来の記号・切り抜き写真を参照する | 目の前の標識や看板と照合しやすくする |
| 人が仕上げる | 運営者が目印を採用/不採用にし、道順・コマ・現地条件を確認する | 企画意図と現地状況を反映して公開する |

AIを使う中心は、**道なりで省略できそうなコマを、紛らわしさに応じて追加で残す判断の補助**である。学習済みのRandomForestをNode.js内で動かし、ルールが必要としたコマは保持する。

経路探索とコマの道路形状はアルゴリズムで作る。生成AIによる道順や図の作成、訪問順の自動最適化は現在の構成に含めない。同じデータ・版・入力条件を揃えることで処理の再現性を確保する。

写真候補にはMapillary側の既存の検出情報を使い、開発PCで切り抜き・整理を済ませる。画像がない固有物は写真候補から外し、出典を保持する。一時停止・横断歩道の取得済み候補は初期採用、信号・固有物写真等は初期不採用とし、道路データに記録された階段の情報は常時表示する。

AIの利用や自動生成ができることは、現地での読みやすさ・安全性、経済効果の保証ではない。運営者の現地確認と利用者による評価を組み合わせる。

## 5. ソリューションの構成図

以下は現在のローカル実装である。データの事前準備と、アプリ利用時の処理を分けている。

~~~mermaid
flowchart TB
    subgraph PREP["開発PCでの事前準備"]
        OSM["OpenStreetMap<br/>道路・スポット・地物"] --> EXTRACT["取得・整理"]
        MAP["Mapillary<br/>検出情報・街路写真"] --> CROP["重複整理・128×128切り抜き"]
    end
    subgraph APP["現在のローカルWebアプリ"]
        STATIC["同梱データ<br/>道路・スポット・目印索引・切り抜き画像"]
        WEB["Next.js + React<br/>運営画面・参加者画面・API"]
        GEN["TypeScriptの生成処理<br/>経路探索・コマ生成・道なり省略"]
        MODEL["同梱の学習済みモデル"]
        DB[("SQLite v8<br/>スポット編集・下書き・コース・公開情報")]
        REVIEW["ローカルJSON<br/>編集中の目印採否"]
        WEB <--> GEN
        WEB <--> DB
        WEB <--> REVIEW
        STATIC --> GEN
        STATIC --> WEB
        MODEL --> GEN
    end
    EXTRACT --> STATIC
    CROP --> STATIC
    OP["運営者のブラウザ"] <--> WEB
    PLAYER["参加者のスマホブラウザ"] <--> WEB
    TILES["OSM背景タイル<br/>外部通信"] -.-> OP
~~~

### データと通信

- 道路・目印候補・切り抜き画像は事前準備して同梱する。ルート生成や候補検索のたびにMapillaryへ通信しない。運営画面の背景地図は外部のOSMタイルを読み込む。
- 作業中の目印採否はローカルJSONへ保存し、コース保存時に採用内容を保存版へ固定する。公開したコースは、後の台帳や下書き変更で書き換えない。
- 参加者の開始記録は同じタブのsessionStorage、画面・地図の表示設定はlocalStorageへ保存する。参加者が撮った写真は各自のスマホに残り、アプリへ収集しない。
- 現在の「公開」は、同じローカルアプリの参加者一覧へ掲載する操作を指す。インターネットへの配信はAWS移行時に別途行う。

### AWS移行との関係

| 項目 | 現状 | 今後の判断・検証 |
| --- | --- | --- |
| Webアプリの配信 | ローカルのNext.jsサーバー | AWS Amplify Hostingが第一候補。実環境で動作・配布サイズ・実行時間を確認する |
| 運営データと採否 | PC上のSQLiteとJSONファイル | 永続保存先と移行方法を選ぶ。Hostingへの配置だけで永続化が完成するとは扱わない |
| 道路・目印・画像 | 版を持つ同梱データと静的ファイル | 出典と版を保って配布し、事前取得と実行時参照の分離を維持する |
| 利用者の入口 | 参加者/運営者の画面を選ぶ。ログイン機能はない | 参加者ログインなしの体験を基本とし、公開環境の運営操作の扱いを整理する |

AWSのDB・認証・ストレージサービスは未選定で、CognitoやAmplify Gen 2の採用を前提にしない。本書で新しいクラウド構成を確定しない。

## 6. 期待する効果と、その確かめ方

| 対象 | 期待する効果 | 効果が生まれる道筋 | 検証方法の例 |
| --- | --- | --- | --- |
| 参加者 | 発見する楽しさ、同行者との会話、まちへの関心 | コマと現地を見比べ、写真を撮り、体験を共有する | 初見の人による操作/歩行テスト、楽しさ・発見した場所のアンケート |
| 運営者 | コース制作と更新の負担軽減 | 地点と訪問順を決めれば、経路・コマの作成を支援できる | 手作業との作成時間・修正回数の比較、説明なしで公開まで進めるかの観察 |
| 店舗・地域 | 未周知の場所への立寄り、飲食・買い物の機会 | コース内の行先や周辺の店に気付く機会が増える | 立寄り先・任意の消費額のアンケート、店舗への聞き取り |
| 三浦市 | 滞在時間の延長、一人当たり観光消費の拡大への寄与 | 食事等の訪問目的に、徒歩で巡る時間と追加の立寄りが加わる | 利用前後や比較条件を設けた滞在時間・立寄り数・消費額の評価 |

これらは期待効果と評価案であり、効果測定の結果や、計測機能の実装済み一覧ではない。開始記録や概算歩行時間だけから、実際の滞在時間や消費額は分からない。撮影や店舗購入を進行の条件にせず、実際の行動変化を確かめる。

コース配置による来訪先の分散も期待できるが、混雑の解消には地域・時間帯・道路事情を踏まえた運用が必要となる。リアルタイム混雑予測・誘導や、宿泊増加の効果は現段階で実現・検証していない。

## 7. 現在できることと、残る確認

| 区分 | 内容 |
| --- | --- |
| ローカルで実装済み | ホームからの役割選択、スポットの地図/一覧・追加/編集/削除、地点と訪問順の設定、経路/コマ生成、到達点補正、目印採否、生成結果の保存、公開/停止/再公開/削除、参加者の開始・コマ閲覧・撮影/ゴール案内 |
| 続けて作成する操作 | コース保存成功後に下書きを空にする。複数の保存済みコースを保持する。歩行時間の表示は時速3kmで概算する |
| 現地で確認すること | 入口、通行可否・安全性、標識や写真の見え方、コマの読みやすさ、営業時間や掲載情報 |
| 運用を決めること | コースの確認/更新担当、ゴールの受付場所・時間・対応方法、素材の公開利用条件 |
| 効果を検証すること | 初見の人の使いやすさ、周遊/滞在/消費への効果、未見コースでのAI補助の有効性 |
| AWS移行で行うこと | 配信互換性、永続保存・データ移行、公開環境の操作権限、費用・運用の確認 |

QR認証・AI写真認証・クーポン/特典は現在の要件から撤回済みである。GPSによる到着認定、ランキング、購入条件、宿泊予約、人流データを使った混雑分析も現在の実装範囲に含まれない。

歩道の存在は道路候補の必須条件にしていない。歩行禁止等の記録を除外していても、データだけで安全性を確認し切れないため、コースの現地確認を公開運用の前提とする。

## 8. 発表で伝えるときの短い説明

三浦に食事や観光で訪れた人が、もう一か所、もう少し長くまちを楽しめるように、コマ地図で巡るウォーキングラリーを開発しました。参加者は道や目印を読み解きながら歩き、写真を撮って発見を共有します。運営者は、訪れてほしいスポットと順番を選び、経路とコマを自動生成して確認・公開できます。AIは紛らわしい道なりのコマを残す判断を補助します。参加者の楽しさと運営者のつくりやすさを両立し、周遊・滞在時間・観光消費機会の拡大を目指します。
