## 1. 対象と今回の範囲

三浦市内の徒歩周遊を、スマートフォンのWebブラウザで楽しめるようにする。観光客は従来型のコマ地図を読み、チェックポイントを認証して進み、条件達成に応じてクーポンを得る。運営者は登録スポットの選択、生成結果の確認、安全性の確認、必要最小限の修正を中心にラリーを公開する。

Phase 1では責務・画面・概念データ・主要フロー・未決定事項を軽量に整理し、アプリ雛形・依存ライブラリの導入・PoC・AWSのセットアップは行わなかった。API仕様、DBスキーマ、詳細な生成アルゴリズムは、それぞれの実装タスクで必要になった範囲だけ設計する。PoC結果と移行案は12節、承認後のP3-01は13節、P3-02は14節、P3-03は15節、P3-04aは16節、P3-05は17節、承認された運営側優先への変更は18節、初期スポット収集は19節、一覧/地図確認は20節を参照する。

要件定義7.1のMVPには観光客と運営者の両方の体験が含まれる。Phase 3の固定データによる観光客向けアプリはその途中成果物であり、全MVPの完成とは扱わない。

初期対象外は、紙のコマ地図出力、ゲーム内アイテム、複雑なミッション生成、ランキング、決済、宿泊予約、高度な個人別最適化。店舗購入を進行条件にしない。AI写真認証・ヒントなどの検討機能は、人間が選択するまで実装対象に含めない。

| 運営者向け画面 | スポット選択・登録、生成条件、生成結果の確認・修正、認証・特典設定、プレビュー・公開・編集。 | Phase 4の必要な画面ごと。 |

## 4. ローカル開発とAWS移行

### 4.1 候補と採用理由

| 項目 | 理由 | 注意点 |
| --- | --- | --- |
| TypeScript | 画面と生成・進行処理のデータ構造を共有し、取り違えを減らせる。 | 型だけでは外部データの正しさや道路の安全性を保証できない。 |
| Next.js + React | ローカルPoCに採用。観光客・運営者の画面と遷移を同じWebアプリで段階的に構築し、Amplify Hostingへの将来配信を検証する。 | SSRの採否を先に固定せず、使う機能とホスティング互換性を確認する。 |
| AWS Amplify Hosting | 最終AWS公開に向けた配信先の第一候補。 | ローカルでの成功をAWS動作保証と扱わず、別途最小構成を検証する。 |
| その他 | Tailwind CSS、地図・描画・経路・QR・テストのライブラリ、ローカルDBは未選定。 | 必要性とPoCの結果に基づき決める。 |

### 4.2 現時点の互換性確認と選定手順

2026-11-06にAWS公式資料を確認した。Amplify Hosting computeのNext.js対応は12〜15と記載され、Edge API Routes／Edge middleware、On-Demand ISR、Next.js streamingなどには非対応の記載がある。これは候補選定のための確認記録であり、採用バージョンの決定ではない。[AWS公式：Next.js対応機能](https://docs.aws.amazon.com/amplify/latest/userguide/ssr-amplify-support.html)

同日のSSRランタイム資料ではNode.js 20・22・24が対応対象で、ビルド時のNode.jsメジャー版に対応するランタイムを使用するとされる。同じ資料の後半にあるClassic（Next.js 11用）の説明と、現行computeの条件を混同しない。[AWS公式：SSR・Node.js対応](https://docs.aws.amazon.com/amplify/latest/userguide/ssr-supported-features.html)

P2-03では上記公式資料と相互互換性・保守状況を再確認し、Next.js 15.5.29／React 19.3.1／Node.js 24.22.2でローカル実行環境を構築した。選定理由と保守期限は[ADR-002](decisions/002-local-web-runtime.md)を参照。今後も最新版を無条件に使わず、対応未確認のSSR・Edge機能に依存しない。

Amplify HostingはWebアプリ配信、Amplify Gen 2は認証・データなどのバックエンド構築として別々に評価する。Hostingを候補にすることからGen 2の採用を導かない。[AWS公式：Hosting概要とバックエンド](https://docs.aws.amazon.com/amplify/latest/userguide/welcome.html)

### 4.3 AWSアカウントなしで進める方法

- Phase 2は検証用スポット・固定データ・モックから始める。道路データの取得は、承認した出典・利用条件に従い、AWSアクセスなしで行える方法を選ぶ。
- Phase 3も固定のラリーを使う。達成記録の保存先は実装前に決め、永続化が必要になった時点でローカルDBを提案する。現時点ではDBを必須にしない。
- ローカル起動・テスト・ビルドに、AWS認証情報、AWS CLIログイン、Amplifyクラウドsandbox、クラウドリソース作成を要求しない。
- 環境変数が必要になったら.env.exampleに名前・用途を示す。.env.localや秘密情報はGit対象外にし、ブラウザへ秘密を渡さない。
- 実行環境が整った時点で、READMEにinstall → start → test → buildの実際のコマンドと前提条件を記載する。今回は実行環境がないため、未検証のコマンドを動作手順として記載しない。

AWS利用可能後は、人間の明示承認を得てから利用開始・リポジトリ接続・リソース作成・デプロイを行う。まずHosting上の最小構成を確認する。DB・認証・画像保存・生成処理の実行場所は、要件、費用・課金リスク、権限、環境変数、運用負荷を比較して選ぶ。永続データ・画像・認証情報の移行方法もその時点で設計する。

| スポット | 再利用する実在地点。ID、名称、施設位置と徒歩到達点、カテゴリ、説明、写真参照、出典/確認状態、チェックポイント利用可否、対応する認証方法。 | 複数ラリーのスタート・ゴール・経由地・チェックポイントとして参照できる。必須登録項目はQ-08。 |
| チェックポイント | あるラリー内で認証対象となるスポットの設定。ID、ラリー参照、スポット参照、訪問順、採用する認証設定。 | スポットとは分離し、同じ場所でもラリーごとに役割・順序・認証条件を変えられる案。達成状態は参加進捗が持つ。 |
| ラリー | 観光客に公開する単位。ID、名称、概要、ルール、開始・終了地点、チェックポイント、ルート参照、推定時間、ゴール・特典条件、公開状態。 | 複数チェックポイント、順序付きルート、特典定義をまとめる。公開版との対応はH-05。 |

関係の中心は「スポットを参照するラリー別チェックポイント」「ラリー → ルート → 順序付きコマ」「ラリー → 参加進捗 → クーポン獲得記録」。一つのチェックポイントを複数の参加が達成するため、スポットやチェックポイント本体に個人の達成フラグを置かない。

CP-06の達成記録とU-10の中断復元は区別する。前者に必要な保存の保証・範囲はPhase 3で決め、デモの一時記録を本番の永続化として報告しない。写真認証を選択するまで、参加者の撮影画像の保存を前提とするデータ構造は作らない。

## 7. 主要処理フロー

### 7.1 ルート・コマ生成から公開まで

1. 登録スポットからスタート・ゴール・チェックポイント・必要な経由地を選び、生成条件をまとめる。
2. 採用した道路情報で、指定地点を通る徒歩経路と経由順を求め、距離・推定歩行時間を計算する。推定時間の算出条件は明示する。
3. 経路と周辺の道路接続情報から分岐・進入・退出方向を取り出し、順序付きコマへ変換する。経路の折れ線だけで周辺の交差点形状を推定して正確な図として示さない。
4. 経路不成立、道路情報不足、形状を確定できない箇所は、生成結果に問題点として示して確認へ戻す。無理に成功扱いにしない。
5. 運営者が全体地図とコマを照合し、歩行可否・危険箇所・立入制限・撮影位置を確認する。データ上の確認と現地確認の範囲を記録する。
6. 必要な修正を行い、認証方式・達成条件・特典と観光客向け表示を確認して公開する。経路やコマを変更した場合は確認し直す案とする。

生成時の完全自動化率や処理時間は未評価。安全性を機械判定だけで保証しない。最小限の修正でも実用になるかをPoCで確かめる。

### 7.2 開始・移動・チェックポイント認証

1. 公開ラリーの詳細・ルールを確認し、参加識別と進捗を用意して開始する。識別方式・開始時の保存方法はQ-13の合意に従う。
2. 進行に対応するコマを表示する。閲覧位置を移しても、認証済み記録は変更しない（H-03）。
3. チェックポイントの説明を確認してQRを読み取り、対象ラリー・チェックポイントに対応するデータかを判定する。順序を制限する場合はその条件も確認する。
4. 成功した場合に達成を記録して進捗へ反映する。誤ったQR、対象違い、読み取り不可、権限拒否、処理失敗では達成を更新せず、結果と再試行を示す。
5. 同じ成功結果の再処理で達成数や特典が意図せず増えないようにする。保証方法は保存先に合わせて設計し、ローカル検証と本番での保証を区別する。
6. 更新後の状態に対して特典条件とゴール条件を評価し、次の案内へ進む。

QRはコードの一致を確認する手段であり、コピーされたコードから現地訪問を保証できない。不正対策の必要水準はD-02で決め、GPS取得などを無断で追加しない。AI写真認証を選ぶ場合は、精度・再試行・画像保持を別途承認してからこの認証手順へ組み込む。

### 7.3 ゴールとクーポン

1. 承認された条件に従ってクーポン獲得を判定する。要件上は途中発行とゴール時発行があり、ゴール画面だけに発行処理を結び付けない。
2. 条件未達成なら発行せず、条件成立なら獲得記録を作って表示する。再表示・再試行での重複発行を防ぐ。同一参加・同一特典を一度に限定するかなどの運用条件はQ-09で決める。
3. ゴール条件を満たしたら参加を終了し、結果と獲得済みクーポンを表示する。ゴール地点のQRなど、具体的な到着確認方法は未決定。
4. クーポン提示・使用済み管理・期限は採用範囲に従う。今回の設計で店舗側の新しい管理アプリは追加しない。

## 10. P2-06b：運営者の確認方法を試す追加PoC（2026-11-07）

ユーザーが、次のタスクに進む前にコマ一覧・全体地図との位置連動・OSM補足情報の追加を依頼したため、P2-06bとして実装する。Phase 4の管理機能へ移行したものではない。

- 確認画面は経路の比較対象と通過位置を一つのメモリー上の状態で保持し、一覧・選択コマ・地図ピン・元道路の照合欄を同期させる。同じnodeでも再訪は通過順に別件。選択位置と次コマまでの点列を強調し、GPS現在地とは区別する。
- 道路探索・分岐抽出・コマ投影は決定的なアルゴリズム。同じコード・固定入力・地点順・設定で再計算できる。固定PoCの訪問順・仮の到着点は手動。現在の下書きでも運営者の並びを採用し、順序最適化は行わない。24節で接続候補の自動計算を追加したが、安全判定は自動化しない。
- 既存道路と同時刻のOSM補足スナップショットを別保存し、表示のみに利用。建物輪郭、施設・店舗・信号等の目印、既存道路の名称と階段を描く。雲形の推測図や架空の入口・横断位置は作らない。
- コマの補足は目印30m以内・最大4件、建物は境界35m以内等から最大12件。P2-06cで標識等の優先と記号・名称の直接表記へ更新した。種別ごとの表示切替で密度を調整し、引出線の先を実座標とし、面のラベル位置は入口としない。細かな情報の出し方はPoC上の実装選択で、本番の最終仕様には確定しない。
- 追加パッケージ・DB・認証・クラウドSDKは導入しない。登録・編集・保存・公開、汎用ルートや最適化、Phase 3・AWSデプロイは別タスク。

実装・検証と未確認事項は[PoC記録14節](poc-route-map.md#p2-06b)を参照。現地の入口・通行・安全性、実測精度、手動参照10件の図の保留を継続し、P2-07とPhase 3は別途着手指示を待つ。

## 11. P2-06c：記号・名称の直接表記（2026-11-07）

## 23. P4-02：地点を選んで作業中の下書きを保存する（2026-11-08）

ユーザーの「次お願いします」と、作業中の下書きは複数不要・完成後はコース生成へ進むとの回答に基づき、1件の作業中下書きを採用する。[ADR-011](decisions/011-working-rally-draft.md)と[運営画面7節](operator-app.md#p4-02)に条件と検証を記録する。

- /operator/draftで台帳の地図/一覧から開始・終了・途中のチェックポイント/経由地を選び、名称とともに明示保存する。開始と終了の共用を許し、途中は任意。同じ途中地点を重複追加せず、役割変更・削除・仮の並びの上下移動を行える。
- /operator/spotsと運営者内のタブで切り替える。既存の地図・検索/カテゴリ/地域と有効な台帳を使い、確認待ち/道路範囲外も保存できる。距離/道順や生成可能の判定を先取りしない。
- 保存時の地点情報を保持し、台帳変更/削除は表示して再確認する。最新情報の反映や保存済みの読直しは明示操作で行い、未保存の入力を勝手に置換しない。削除済みは外すか選び直し、再保存する。
- 既存のSQLiteファイルを形式v3へ移し、スポット編集/削除を保って下書きテーブルを追加する。台帳照合・下書きの版照合・保存/読戻しを同じトランザクションで行う。同じ内容の再送は最初の版/日時を維持する。
- 既存の固定コース/参加記録、道路/コマ生成、写真は維持する。途中の仮の並びから生成の訪問順を確定せず、自動順序決定とルート/コマ生成はP4-03aで条件を確認する。

P4-02の検証・自己レビュー・コミット後に停止する。次の提案はP4-03aの生成条件と訪問順決定の確認とする。


## 24. 道路範囲・自動接続候補と訪問順（P4-03b-1）

2026-11-09のユーザー回答により、P4-03aより道路・到達点拡張を先行する。訪問順は開始→下書きの途中地点の並び→終了とし、地点間の最短徒歩経路だけをアルゴリズムで求める。[ADR-012](decisions/012-expanded-road-connections.md)がH-02と23節の順序保留を更新する。

- 拡張道路/建物/目印/標識の固定データは既存PoCと別保存。元データ約7.1MBから経路計算向け約0.88MBをオフライン生成し、取得時点/クエリ/ハッシュを保存する。
- lib/route/road-connection.tsは許容有向辺を線分化し、近傍点と直線距離を再現可能に計算する。lib/miura-road-connections.tsは固定データを読む境界、読取りAPIは現在の台帳と照合する。
- 道路IDをスポットの必須入力に追加しない。初期・追加・座標変更後のスポットに同じ計算を適用。派生候補はDBへ保存せず、現在のID/版/座標・道路データ版と結び付けて扱う。
- スポット管理と下書きに候補の距離/状態/出典・地図の線分/丸/参照点線を表示。候補点を入口や安全な接続として確定しない。表示は元施設位置を保持し、古い非同期結果を排除する。
- 既存の旧PoC3地点、固定コース31コマと参加記録を維持する。新たな178候補を生成可能数と表現しない。

幾何候補だけでは、入口・障害物・敷地内動線・通行状況・到達可能性を確定できない。候補点のグラフ組込みと採否/修正、拡張地域のルート/コマ・周辺情報の照合は後続。詳細と検証は[運営画面8節](operator-app.md#p4-03b-1)と[データ記録](../data/miura-expanded/README.md)を参照。今回の文書・実装・検証・コミット後は停止する。


## 25. 道路候補の一時グラフへの組込み（P4-03b-2）

P4-03b-1の次の着手指示を受け、24節の候補点を経路探索へ利用する計算基礎を追加した。[運営画面9節](operator-app.md#p4-03b-2)に仕様と固定データの評価を記録する。

- 元の歩行グラフと候補のデータ版・元線分/座標/方向を照合し、候補の位置で有向辺を分割する。方向を増やさず、元の距離を割合で配分する。施設→道路の直線は歩行辺にしない。
- 元の頂点・道路タグ・分岐・制約を残した一時グラフを作り、元グラフを変更しない。候補同士が同じ元線分の同座標なら同一ノード、異なる道路なら同座標でも別ノードとする。端点は元ノードを再利用する。
- 一時IDと、元道路ID/両端/割合の対応を返す。OSMの原典IDとは区別する。開始と終了は同じスポットを利用でき、訪問IDと施設IDを分ける。訪問順の最適化は追加しない。
- 拡張固定データからの準備はlib/miura-road-connections.tsで行い、ファイル読込み・ハッシュ照合と汎用の線分分割を分ける。保存/クラウド/新しいサービス依存は発生しない。
- オフラインのconnections:reportで178件の候補と全31,506有向組合せを評価。最大163件の相互到達グループと別の15件を確認した。道路グラフの到達可能は入口/安全性や施設への接続の確認済みを意味しない。

今回は未確認候補によるローカルの計算検証まで。候補の採否/修正UI、可変下書きからの生成プレビュー・全域コマ照合は後続。到達不能を直線や地点の省略で補わない。画面・既存デモコース・DB形式v3・固定データは維持する。


## 26. 保存済み下書きからの生成プレビュー（P4-03a）

[ADR-013](decisions/013-saved-draft-preview.md)のA案承認により、未確認の自動候補で生成する確認用の画面を追加した。操作/責務・検証は[運営画面10節](operator-app.md#p4-03a)参照。

- 下書きの保存後に/operator/previewへ進む。下書きと台帳を同じ読取トランザクションで読み、選択地点の変更/削除を照合する。下書きの表示順を保ち、一時グラフの道路上候補間を経路探索する。
- 到達不能や全区間0mでは明示停止する。一部0mや開始/終了の共用は維持する。データ読込み失敗で初期化・旧結果表示を行わない。
- 既存の分岐抽出・元枝/角度を保つコマ描画を再利用し、保留も含め一覧へ残す。コマ結合だけを共有モジュールへ移す。全体地図と選択コマ・次のコマまでの道路・訪問地点を同期する。
- 拡張固定データの局所的な建物/目印/標識/階段等を、既存条件でコマへ表示する。元ファイル全体やGraph/Mapはブラウザへ渡さない。SVGの全体地図は新たなタイル通信を必要としない。
- 施設位置と道路候補、参照用直線と歩行距離を区別する。道路途中の一時IDは原典OSMノードと区別する。各コマから元の道路/地点へ参照できる。
- 生成モデルと選択状態は画面内だけで保持し、元にした下書き版/保存日時を示す。保存結果や確認済みフラグは書かない。再生成時に現在の保存内容を読む。

入口/施設までの通路・通行/安全性、候補修正、全域の形状照合、生成結果の保存/公開とAWS互換性は後続。参加者側の追加開発・Phase 3保留は継続する。


## 27. 下書き用の道路到達点の修正（P4-04）

[ADR-014](decisions/014-draft-road-corrections.md)のA案を承認済み。操作・保存・検証は[運営画面11節](operator-app.md#p4-04)に記録する。

- 概念データとして、施設位置と別に「下書きの道路到達点の補正」を持つ。同じ施設を複数役割で使うときは共用し、施設位置や訪問順を変えない。

## 29. 短い枝の表示方式比較（P4-04b）

[方式比較](koma-presentation-options.md)に、短い選択枝のため保留になった45コマのA/Bを記録した。Aは30m参照図＋自動拡大図、Bは30m固定＋外側ラベル。これは比較時点の記録で、現在はA案を承認し30節の範囲で適用した。比較時点では実アプリ・歩行条件・保存を変更していない。

Aは元の形状/全枝・道路上の黒点/矢印を保てる推奨候補。周辺情報が見切れるため30m参照図を残し、建物/目印/階段は道路と同倍率で扱う条件を提案する。数値上の枝長条件の通過を、実端末での可読性や現地安全性の合格とは扱わない。

採用承認後は運営者プレビューの短い枝による保留だけへ適用する案。通常コマ・参加者側・固定PoCを保持し、方向不明/欠落/不整合などは保留を継続する。現在のADR-003への例外となる表示判断は、比較資料をレビューして人間が選び、承認時にADRへ記録する。

## 30. 運営者の短い枝の拡大表示（P4-04c）

ユーザーがA案を承認。[ADR-015](decisions/015-operator-koma-expansion.md)にADR-003への運営者向けの限定例外を記録し、[運営画面14節](operator-app.md#p4-04c)に実装/検証を集約した。

- 通常の生成は従来の保留を維持し、運営者プレビューだけが、短い枝で止まる前の検証済み30m形状を参照用に保持する。未知方向/欠落/不整合を描き足さない。
- 実表示幅から拡大率を決め、道路/建物/目印/階段を同倍率で扱う。元点列の前方部分と道路ID/割合・全枝/役割・距離を保つ。通常コマと固定PoC/参加者側の表示を保持する。
- 周辺30mの参照図と目印一覧を残す。拡大しても記号を区別しにくい場合は保留する。元のheldは30m図の状態であり、拡大の表示可否と現地の安全性を同一視しない。
- 表示状態・生成結果を保存せず、DB形式v4や下書き/補正、歩行条件・外部依存は変更しない。現地/実端末での読解と公開可否は後続。
