## 1. 対象と今回の範囲

三浦市内の徒歩周遊を、スマートフォンのWebブラウザで楽しめるようにする。観光客は従来型のコマ地図を読み、チェックポイントを認証して進み、条件達成に応じてクーポンを得る。運営者は登録スポットの選択、生成結果の確認、安全性の確認、必要最小限の修正を中心にラリーを公開する。

Phase 1では責務・画面・概念データ・主要フロー・未決定事項を軽量に整理し、アプリ雛形・依存ライブラリの導入・PoC・AWSのセットアップは行わなかった。API仕様、DBスキーマ、詳細な生成アルゴリズムは、それぞれの実装タスクで必要になった範囲だけ設計する。PoC結果と移行案は12節、承認後のP3-01は13節、P3-02は14節、P3-03は15節、P3-04aは16節、P3-05は17節、承認された運営側優先への変更は18節、初期スポット収集は19節、一覧/地図確認は20節を参照する。

要件定義7.1のMVPには観光客と運営者の両方の体験が含まれる。Phase 3の固定データによる観光客向けアプリはその途中成果物であり、全MVPの完成とは扱わない。

初期対象外は、紙のコマ地図出力、ゲーム内アイテム、複雑なミッション生成、ランキング、決済、宿泊予約、高度な個人別最適化。店舗購入を進行条件にしない。AI写真認証・ヒントなどの検討機能は、人間が選択するまで実装対象に含めない。

## 3. システムの責務

以下は論理的な責務の整理であり、別サービスや大規模なレイヤー構成を要求しない。

| 責務 | 担当する内容 | 依存を分ける時点 |
| --- | --- | --- |
| 観光客向け画面 | 一覧・概要、コマとチェックポイント、認証結果、進捗、ゴール、クーポンの表示。屋外で読みやすく、歩行中の操作を減らす。 | 画面実装時に表示と進行判定を分ける。 |
| 運営者向け画面 | スポット選択・登録、生成条件、生成結果の確認・修正、認証・特典設定、プレビュー・公開・編集。 | Phase 4の必要な画面ごと。 |
| ラリー進行・特典判定 | 対象ラリーとチェックポイントの整合、達成記録、ゴール条件、クーポン獲得条件を扱う。 | Phase 3の進行処理時。クラウドSDKから独立させる。 |
| ルート・コマ生成 | スポットと条件から経由順・徒歩経路を求め、道路情報から分岐・進行方向・距離を抽出してコマを生成する。 | Phase 2で外部道路・経路サービスの利用が発生した時。 |
| 訪問認証 | QRの判定結果を進行処理へ渡す。写真方式を採用した場合も同じ目的の手段として扱う。 | QR、写真それぞれの実装時。写真ミッション機能は作らない。 |
| データ・画像・アクセスの管理 | スポット、ラリー、進捗、画像を保存し、運営者の操作権限を確認する。 | 固定データから実際の保存・認証が必要になった時。 |

UIや中核ロジックへAWS・経路サービスのSDKを直接埋め込まない。実際に外部依存が生じた処理の入出力だけを小さく分離し、先回りした汎用アダプタ群は用意しない。

## 4. ローカル開発とAWS移行

### 4.1 候補と採用理由

| 項目 | 理由 | 注意点 |
| --- | --- | --- |
| TypeScript | 画面と生成・進行処理のデータ構造を共有し、取り違えを減らせる。 | 型だけでは外部データの正しさや道路の安全性を保証できない。 |
| Next.js + React | ローカルPoCに採用。観光客・運営者の画面と遷移を同じWebアプリで段階的に構築し、Amplify Hostingへの将来配信を検証する。 | SSRの採否を先に固定せず、使う機能とホスティング互換性を確認する。 |
| AWS Amplify Hosting | 最終AWS公開に向けた配信先の第一候補。 | ローカルでの成功をAWS動作保証と扱わず、別途最小構成を検証する。 |
| その他 | Tailwind CSS、地図・描画・経路・QR・テストのライブラリ、ローカルDBは未選定。 | 必要性とPoCの結果に基づき決める。 |

### 4.2 現時点の互換性確認と選定手順

2026-11-06にAWS公式資料を確認した。Amplify Hosting computeのNext.js対応は12〜15と記載され、Edge API Routes／Edge middleware、On-Demand ISR、Next.js streamingなどには非対応の記載がある。これは候補選定のための確認記録であり、採用バージョンの決定ではない。[AWS公式：Next.js対応機能](https://docs.aws.amazon.com/amplify/latest/userguide/ssr-amplify-support.html)

同日のSSRランタイム資料ではNode.js 20・22・24が対応対象で、ビルド時のNode.jsメジャー版に対応するランタイムを使用するとされる。同じ資料の後半にあるClassic（Next.js 11用）の説明と、現行computeの条件を混同しない。[AWS公式：SSR・Node.js対応](https://docs.aws.amazon.com/amplify/latest/userguide/ssr-supported-features.html)

P2-03では上記公式資料と相互互換性・保守状況を再確認し、Next.js 15.5.29／React 19.3.1／Node.js 24.22.2でローカル実行環境を構築した。選定理由と保守期限は[ADR-002](decisions/002-local-web-runtime.md)を参照。今後も最新版を無条件に使わず、対応未確認のSSR・Edge機能に依存しない。

Amplify HostingはWebアプリ配信、Amplify Gen 2は認証・データなどのバックエンド構築として別々に評価する。Hostingを候補にすることからGen 2の採用を導かない。[AWS公式：Hosting概要とバックエンド](https://docs.aws.amazon.com/amplify/latest/userguide/welcome.html)

### 4.3 AWSアカウントなしで進める方法

- Phase 2は検証用スポット・固定データ・モックから始める。道路データの取得は、承認した出典・利用条件に従い、AWSアクセスなしで行える方法を選ぶ。
- Phase 3も固定のラリーを使う。達成記録の保存先は実装前に決め、永続化が必要になった時点でローカルDBを提案する。現時点ではDBを必須にしない。
- ローカル起動・テスト・ビルドに、AWS認証情報、AWS CLIログイン、Amplifyクラウドsandbox、クラウドリソース作成を要求しない。
- 環境変数が必要になったら.env.exampleに名前・用途を示す。.env.localや秘密情報はGit対象外にし、ブラウザへ秘密を渡さない。
- 実行環境が整った時点で、READMEにinstall → start → test → buildの実際のコマンドと前提条件を記載する。今回は実行環境がないため、未検証のコマンドを動作手順として記載しない。

AWS利用可能後は、人間の明示承認を得てから利用開始・リポジトリ接続・リソース作成・デプロイを行う。まずHosting上の最小構成を確認する。DB・認証・画像保存・生成処理の実行場所は、要件、費用・課金リスク、権限、環境変数、運用負荷を比較して選ぶ。永続データ・画像・認証情報の移行方法もその時点で設計する。

既存スポットと基本条件から自動生成し、個々のコマの手入力を標準手順にしない。公開済みラリーも編集できるが、再確認と参加中データの扱いはD-03の承認後に具体化する。運営者認証・認可の方式は未決定であり、実利用の管理画面を無保護で公開しない。

## 6. 概念データモデル

項目は責務と関係を説明する候補。必須入力、物理テーブル、型、API、保存方式を確定するものではない。

| 概念 | 役割・代表的な情報 | 主な関係 |
| --- | --- | --- |
| スポット | 再利用する実在地点。ID、名称、施設位置と徒歩到達点、カテゴリ、説明、写真参照、出典/確認状態、チェックポイント利用可否、対応する認証方法。 | 複数ラリーのスタート・ゴール・経由地・チェックポイントとして参照できる。必須登録項目はQ-08。 |

関係の中心は「スポットを参照するラリー別チェックポイント」「ラリー → ルート → 順序付きコマ」「ラリー → 参加進捗 → クーポン獲得記録」。一つのチェックポイントを複数の参加が達成するため、スポットやチェックポイント本体に個人の達成フラグを置かない。

CP-06の達成記録とU-10の中断復元は区別する。前者に必要な保存の保証・範囲はPhase 3で決め、デモの一時記録を本番の永続化として報告しない。写真認証を選択するまで、参加者の撮影画像の保存を前提とするデータ構造は作らない。

## 7. 主要処理フロー

### 7.1 ルート・コマ生成から公開まで

1. 登録スポットからスタート・ゴール・チェックポイント・必要な経由地を選び、生成条件をまとめる。
2. 採用した道路情報で、指定地点を通る徒歩経路と経由順を求め、距離・推定歩行時間を計算する。推定時間の算出条件は明示する。
3. 経路と周辺の道路接続情報から分岐・進入・退出方向を取り出し、順序付きコマへ変換する。経路の折れ線だけで周辺の交差点形状を推定して正確な図として示さない。
4. 経路不成立、道路情報不足、形状を確定できない箇所は、生成結果に問題点として示して確認へ戻す。無理に成功扱いにしない。
5. 運営者が全体地図とコマを照合し、歩行可否・危険箇所・立入制限・撮影位置を確認する。データ上の確認と現地確認の範囲を記録する。
6. 必要な修正を行い、認証方式・達成条件・特典と観光客向け表示を確認して公開する。経路やコマを変更した場合は確認し直す案とする。

生成時の完全自動化率や処理時間は未評価。安全性を機械判定だけで保証しない。最小限の修正でも実用になるかをPoCで確かめる。

### 7.2 開始・移動・チェックポイント認証

1. 公開ラリーの詳細・ルールを確認し、参加識別と進捗を用意して開始する。識別方式・開始時の保存方法はQ-13の合意に従う。
2. 進行に対応するコマを表示する。閲覧位置を移しても、認証済み記録は変更しない（H-03）。
3. チェックポイントの説明を確認してQRを読み取り、対象ラリー・チェックポイントに対応するデータかを判定する。順序を制限する場合はその条件も確認する。
4. 成功した場合に達成を記録して進捗へ反映する。誤ったQR、対象違い、読み取り不可、権限拒否、処理失敗では達成を更新せず、結果と再試行を示す。
5. 同じ成功結果の再処理で達成数や特典が意図せず増えないようにする。保証方法は保存先に合わせて設計し、ローカル検証と本番での保証を区別する。
6. 更新後の状態に対して特典条件とゴール条件を評価し、次の案内へ進む。

QRはコードの一致を確認する手段であり、コピーされたコードから現地訪問を保証できない。不正対策の必要水準はD-02で決め、GPS取得などを無断で追加しない。AI写真認証を選ぶ場合は、精度・再試行・画像保持を別途承認してからこの認証手順へ組み込む。

### 7.3 ゴールとクーポン

1. 承認された条件に従ってクーポン獲得を判定する。要件上は途中発行とゴール時発行があり、ゴール画面だけに発行処理を結び付けない。
2. 条件未達成なら発行せず、条件成立なら獲得記録を作って表示する。再表示・再試行での重複発行を防ぐ。同一参加・同一特典を一度に限定するかなどの運用条件はQ-09で決める。
3. ゴール条件を満たしたら参加を終了し、結果と獲得済みクーポンを表示する。ゴール地点のQRなど、具体的な到着確認方法は未決定。
4. クーポン提示・使用済み管理・期限は採用範囲に従う。今回の設計で店舗側の新しい管理アプリは追加しない。
